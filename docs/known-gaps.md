### 完整的楼梯图

把 51 层的楼梯连起来看，**楼梯图只在 3 处断开，而且全部落在「区域边界 BOSS 层」**：

| 断点 | 所在位置 | 声明方式 | 数据支撑 |
|---|---|---|---|
| **10 → 11** | 一区 BOSS 层（骷髅队长） | `event` 剧情生成楼梯 | ✅ 有源码依据（`floor[10][115]=4`），已写成 `f10-zone1-clear` |
| **40 → 41** | 四区 BOSS 层（骑士队长） | `teleport` | ✅ 已写成 `f40-zone4-clear`（按 §1「统一修法」） |
| **49 → 50** | 假魔王层 | `teleport` | ✅ 已写成 `f24-gate-to-50`（方案 A：入口在第 24 层红门空腔） |

除此之外，第 2~9、11~39、41~48 层的上下楼梯**完全连续**。

### 这个断法显然是刻意的

三个断点全部位于「一区 / 四区 / 五区」的边界，且都是 BOSS 层 —— 这与「**打完 BOSS 才开启通往下一区的路**」
这一经典设计手法完全吻合。**这不是数据损坏，是设计意图；参考实现的缺陷只在于「只实现了其中一个」。**

对照参考源码：`event.js` 中 `eventHappened[7]` 分支执行 `floor[10][115] = 4`，
正是第 10 层生成上楼梯的实现。**11 层以后的同类事件，参考实现没有写。**

### 为什么 49 → 50 是最严重的

| 候选机制 | 能否从 49 到 50 | 说明 |
|---|---|---|
| 上楼器（45 层取得，`changeFloor +1`） | 理论可以 | ❌ 但它是**一次性**的，攻略明确指定用在 43 层开启 44 层隐藏层 |
| 楼层传送器（`range [1, 49]`） | **不能** | 范围上限就是 49；**且它只能去 `wentFloor` 里已到过的楼层**，无法用于首次向上推进 |
| 上楼梯 | **不能** | `floor[49]` 地形只有编号 3（下楼梯），没有编号 4 |

**结论：按当前数据，玩家打完假魔王后无法进入第 50 层，真魔王永远遇不到。**

> 顺带纠正一个容易搞错的点：**楼层传送器不能充当向上出口。**
> 它只显示「到过的楼层」（`wentFloor`），是**回溯**工具而非**推进**工具 ——
> 这正好解释了攻略里那句「上40层，**目的是以后**可用电梯直上」：先到该层登记，之后才能跳回来。

## 6. 已排除的「伪缺口」

以下几项**看起来像 bug，但已验证为原版设计或可解**。记录在此以免重复排查。

### 6.1 ✅ 第 44 层神圣盾密室不是死锁

**初判**：神圣盾 `(5,5)` 及周围 4 瓶红药水所在的十字形密室被 18 格墙完全包围，从入口 BFS 不可达（可达 97/121）。

**复核结论：可以用铁锹进入。** 从 `(5,8)` 或 `(6,7)` 站位，用铁锹挖开 `(5,7)`，
即可走 `(5,8) → (5,7) → (5,6) → (5,5)` 进入密室。铁锹在第 15 层（大乌贼守着）可获得。

**所以这是一道「破墙」谜题，不是死锁。** 只是 `floor-notes` 的原描述（「用炸弹清掉守卫」）
只提到了清掉两个 `def 360` 的高级卫兵，**没有提到如何进入密室**，容易误导。建议补充说明。

### 6.2 ✅ 第 30 层没有下楼梯 —— 与「特殊楼层单向进入」的设计惯例一致

`floor[30]` 有 2 个上楼梯、**0 个下楼梯**，而 `floor[29]` 有上楼梯到 30。
即 **29 → 30 是单向的**：进入 30 层后无法用步行回到 29 层。

**不构成死锁**，因为 `floorTeleporter`（范围 `[1,49]`）在第 1 层 `(1,10)` 就能取得，
玩家早在抵达 30 层之前就持有它 —— 而传送器能回溯到已到过的 29 层。

**再看一遍全塔「缺下楼梯」的楼层，会发现它是一个统一的惯例：**

| 层 | 缺下楼梯的原因 |
|---|---|
| 0 | 地下室，只能用下楼器从 1 层进入 |
| 1 | 起点，下方无楼层 |
| **30** | **待确认** |
| 44 | 隐藏层，单向进入（只能靠上楼器 / 43 层楼梯） |
| 50 | 终点，进入后不再离开 |

除 30 层外，每一层「缺下楼梯」都有明确的设计理由。**推测 30 层同理**（它是三区与四区之间的枢纽层，
中央横排 6 只史莱姆 + 一扇自动门，结构上像一道「门槛」），但**没有找到决定性证据**。

`data/floor-notes.json` 的 `"30"` 条目已记录该现象，并标注 `status: "unverified"`。

→ **待办：若要严格复刻，需确认原版第 30 层是否有下楼梯。否则建议按「设计意图」接受现状。**

### 6.3 ✅ 第 43 层到第 44 层有正常楼梯，与「44 层是隐藏层」的说法冲突

**数据事实**：`floor[43]` 在 `(0,10)` 有上楼梯 → 44；`floor[44]` 有上楼梯 → 45，但**没有下楼梯**。

**攻略说法**：「44 层是特殊隐藏层，飞行器列表里不会出现……得靠上楼器才能到」；
`floor-notes` 也记为「在本层（43）使用上楼器可到达隐藏的 44 层」。

**两种解读**（数据不足以判定）：

| 解读 | 说明 |
|---|---|
| ① 原版确实有 43→44 楼梯 | 「隐藏」指的是**不在楼层传送器列表里**（`wentFloor` 不记录、传送面板不出现），且 44 层**无下楼梯**（单向）。数据完全支持这一解读。 |

## 7. 建议的 overlay 机制（解决「忠实于源」与「修正缺口」的冲突）

上面多个方案都指向同一个工程问题：

> 直接改 `data/floors/*.json` 会让派生数据偏离参考源，而且**重新运行 `import-mota50.mjs` 时会被覆盖**。
> 但不改，游戏就有硬缺口。

### 建议做法：加一层覆盖文件

```
data/
  overrides.json          ← 手写，记录对参考源的所有「有意偏离」
tools/
  import-mota50.mjs       ← 导入最后一步套用 overrides
```

```jsonc
{
  "$comment": "对参考源码的有意修正。每条必须写 why，保证「已知偏离」始终可审计。",
  "monsters": [
    {
      "floor": 20, "at": { "x": 5, "y": 5 },
      "id": "vampire",
      "why": "参考源码从未放置二区 BOSS 吸血鬼；第20层 (5,5) 为空且被 8 只大蝙蝠环绕，是 BOSS 位。见 docs/known-gaps.md §2"
    }
  ],
  "events": [ /* … */ ],
  "npcs":   [ /* … */ ]
}
```

这样能得到：

- ✅ **重新导入不会丢失修正**（overrides 在导入后套用）
- ✅ **偏离永远可审计**（每条都带 `why` 指向本文件）
- ✅ **校验器可以检查 overrides 的完整性**（比如「所有 override 的目标格必须原本为空」）

## 10. 事件表如何落地（`data/events.json` → 引擎）

事件表不是孤立的数据文件，它有一条完整的「数据 → 引擎 → 状态」链路，缺一环就会「数据写了但游戏不认」：

| 环节 | 文件 | 做了什么 |
|---|---|---|
| 数据 | `data/events.json` | 4 条事件（`f10-zone1-clear` / `f40-zone4-clear` / `f24-gate-to-50` / `f49-seal-break`） |
| 类型 | `src/data/types.ts` | `GameEvent` / `EventEffect`（`addStair`）/ `ReplaceMonsterEffect`（`replaceMonster`）；`GameData.events` 字段 |
| 读取 | `src/data/index.ts` + `runtime-files.mjs` + `source-web.ts` | 把 `events.json` 纳入运行时数据清单 |
| 引擎 | `src/game/engine/events.ts` | `applyTrigger` 匹配 `defeated` / `allDefeated` / `start`，执行 `addStair`（写 `state.extraStairs`）与 `replaceMonster`（写 `state.monsterSwap`） |
| 状态 | `src/game/state.ts` | `extraStairs` + `monsterSwap` + `fired` 三个新字段；`entityAt`/`livingMonsters` 优先读 `monsterSwap`；`stairsOn` 合并读数据楼梯与 `extraStairs` |
| 触发 | `src/game/engine/step.ts` | 击败怪物后 `applyTrigger(defeated)` + `applyTrigger(allDefeated)`；换层判定改用 `stairsOn` |

**两个最容易踩的坑**（都已在实现时规避）：

1. **`allDefeated` 必须限定 `floor`** —— 守卫 `darkKnight` 全塔 12 只、`seniorWizard` 14 只，
   不限定第 49 层统计会永不解封。`f49-seal-break` 的 trigger 带 `floor: 49`。
2. **`replaceMonster` 不标 `removed`** —— 真身出现 ≠ 被打败，`entityAt` 里 `monsterSwap` 检查要
   **先于** `removed` 检查，否则假魔王被换成真魔王后那一格读出来是 null。
