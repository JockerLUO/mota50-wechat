## 1. 数据来源与核对方法

本项目的数值**不是凭记忆写的**，也不是从单一来源抄的。每一条数值都至少经过两处独立来源交叉：

| 来源 | 性质 | 用途 |
|---|---|---|
| `reference/mota50/source/mota50-role.js` | 参考源码（GPL-3.0） | 怪物 33 只的 HP/ATK/DEF/金币的**主来源** |
| [h5mota 论坛原版50层基准数值帖](https://h5mota.com/bbs/thread/?tid=1551) | 社区实测 | 交叉核对怪物数值、经验值、钥匙收支、金币预算 |
| 百度百科《魔塔50层》 | 百科整理 | 与基准帖逐条比对（两者一致） |
| `motajs/mota-js` `libs/enemys.js` | 标准引擎（BSD-3） | **战斗公式**的权威实现 |
| 《魔塔50层》全攻略（逐层流程） | 玩家实测 | 战斗扣血的**第三方验证值**（见 §3.4） |

> **为什么必须交叉核对：** 参考源码 `mota50-fight.js` 的战斗实现是错的（只扣一回合伤害，没算回合数）。
> 如果只信一个来源，整个数值体系会系统性偏差。详见 §3.3。

### 参考源码的两个已知不完整之处

| 问题 | 证据 | 处理 |
|---|---|---|
| 战斗公式错误 | `mota50-fight.js` 中 `player.hp -= (enm.att - player.def)` 后直接返回，无回合数循环 | 弃用，改用 `motajs/mota-js` 公式 |
| 事件只实现前 10 层 | `mota50-event.js` 的 `eventHappened` 分支仅覆盖 1~10 层相关剧情 | 11 层以后的楼层机制改从攻略文字考证，记录在 `data/floor-notes.json` |

## 2. 成长模型：无经验、无等级

**原版《魔塔50层》没有经验值与等级系统。** 这不是疏漏，是设计选择。

三处独立来源一致：

1. 参考源码 `player` 对象只有 `att / def / hp / coin / yellowKey / blueKey / redKey / sword / shield / item`，**没有 `exp`、`level` 字段**。
2. `mota50-fight.js` 击杀后只累加 `player.coin`，不累加经验。
3. h5mota 基准帖中**全部怪物经验值均为 0**。

因此 `data/monsters.json` 中所有怪物的 `exp` 字段固定为 `0`，`data/constants.json` 中
`progression.hasExperience = false`、`progression.hasLevel = false`。

### 勇者成长的三条唯一途径

| 途径 | 增量 | 说明 |
|---|---|---|
| **商店购买** | HP+100 / ATK+2 / DEF+4（一楼层系数） | 唯一可用金币换属性的地方，全局仅约 17 次 |
| **宝石** | 红宝石 ATK+2、蓝宝石 DEF+2 | 地图上固定分布，不可再生 |
| **剑与盾** | 铁剑+10 / 银剑+20 / 骑士剑+40 / 圣剑+50 / 神圣剑+100<br>铁盾+10 / 银盾+20 / 骑士盾+40 / 圣盾+50 / 神圣盾+100 | 一次性大额提升，是区域难度的台阶 |

> **设计含义：** 因为没有经验值，玩家**无法靠刷怪变强**。打怪只在「必须打通这条路」或「为了金币」时才值得做。
> 这直接造就了魔塔的核心体验：**每一次战斗都是在消耗不可再生的生命去换有限的资源**，绕路与取舍比战斗本身更重要。

## 3. 战斗公式

### 3.1 核心式子

魔塔的战斗是**确定性回合制，无随机数** —— 这正是「伤害预判」能成立的前提。

```
perHit   = hero.atk − mon.def              勇者每回合对怪造成的伤害
perRound = max(0, mon.atk − hero.def)      怪物每回合对勇者造成的伤害
rounds   = ⌈mon.hp / perHit⌉               击杀所需回合数
hpLoss   = (rounds − 1) × perRound         勇者的生命损失
```

### 3.2 为什么是 `(rounds − 1)` 而不是 `rounds`

**勇者先手。** 第 `rounds` 回合是致命一击，怪物在出手前就已经倒下，所以怪物实际只完整出手 `rounds − 1` 次。

这是全项目最容易写错、影响也最大的一行。写成 `rounds × perRound` 会让预判系统性偏高。

标准引擎 `motajs/mota-js` 的等价写法：

```js
turn = parseInt((mon_hp - 1) / (hero_atk - mon_def))   // = rounds − 1
ans  = initDamage + turn * per_damage
```

### 3.3 参考实现的错误（本项目明确不采用）

`reference/mota50/source/mota50-fight.js`：

```js
if( player.hp > (enm.att - player.def) ){   // 只判断「能不能扛住一回合」
    ...
    player.hp -= (enm.att - player.def);    // 然后只扣一回合，直接返回
    return true;
}
```

它**完全没有计算回合数**。用它做数值预期会严重低估损失（血量厚的怪尤其明显）。
所以本项目：参考源码只取**怪物数值与地图数据**，**战斗公式一律以标准引擎为准**。

### 3.4 第三方实测验证

`data/combat-cases.json` 中共 21 条战斗黄金用例，其中 **17 条的 `expected` 值直接取自攻略中玩家的实测扣血量**，
属于独立于上述两个源码的第三方验证。摘录：

| 用例 | 场景 | 期望扣血 | 来源 |
|---|---|---|---|
| 绿史莱姆×1 | 初始属性 1000/10/10 | 24 | 攻略实测 |
| 兽人（持十字架） | ATK 10 翻倍为 20 | 3 | 攻略实测 |
| 兽人武士（持十字架） | 实测数字 264 → 76 | 76 | 攻略实测 |
| 吸血鬼（持十字架） | 实测数字 575 | 575 | 攻略实测 |
| 魔法警卫 | 夹击 50% 概率 | 期望 1100 / 最坏 1320 | 攻略实测 |

校验器会跑这 21 条用例，**任何一侧公式改动而另一侧没跟上就会立即报错**。

### 3.5 打不动的判定（数值门）

若 `perHit <= 0`（即 `hero.atk <= mon.def`），永远无法击杀 → 返回 `canWin: false, reason: 'unpierceable'`，损失记为 `Infinity`。

**这不是 bug，而是魔塔控制节奏的主要手段。** 典型例子：

- **石头人 def 68** → 攻击力 ≤ 68 时完全无法击破，第 19 层的十字架路线被封死，逼迫玩家先堆攻击力。
- **高级卫兵 def 360** → 第 44 层隐藏层（神圣盾所在）的门槛。

UI 必须在鼠标悬停/站定时就把这个状态标出来（`core/combat.mjs` 的 `grade()` 返回 `'blocked'`），
而不是让玩家撞上去才发现。

### 3.6 特殊机制对公式的修正

| 机制 | trait | 影响对象 | 修正 |
|---|---|---|---|
| **十字架** | `crossVulnerable` | 兽人、兽人武士、吸血鬼 | 持十字架时对其攻击力 ×2 |
| **屠龙剑** | `dragon` | 魔龙 | 持屠龙剑时攻击力 ×2 |
| **神圣盾** | `immune: aura` | — | 免疫巫师领域伤害 |
| **领域** | `aura` | 初级巫师(dmg 100)、高级巫师(dmg 200) | 勇者**每移动一步**、若与之相邻则扣固定 HP，不进战斗结算 |
| **夹击** | `flank` | 高级巫师(0.5)、魔法警卫(0.5) | 战斗前按概率先制攻击一次 |
| **斩杀** | `execute` | 双手剑士 | 勇者 ATK ≥ 150 时损失归零 |

**领域是「走路扣血」而非「战斗扣血」** —— 它与战斗结算完全分离，在移动 reducer 中处理
（`core/combat.mjs` 的 `auraStepDamage()`）。这是原版后期最耗血的机制，也是神圣盾价值的来源。

**夹击是概率性的**，因此 `simulateBattle` 同时返回 `hpLossMin` / `hpLossMax` / `hpLoss`（期望值），
不做「假装确定」的简化。

### 3.7 目标区间（非原版硬指标）

`data/constants.json` 的 `designTargets.lossRatioPerFloor = [0.05, 0.15]`，
是**通用魔塔手感区间**，不是原版实测值。原版实际更激进（后期单怪可占 30%+）。
调数值时用 `tools/balance-check.html` 观察实际曲线，不要硬套这个区间。

## 4. 商店定价与经济

### 4.1 定价公式

```
cost(n) = 10 · n · (n − 1) + 20          n = 已购买次数，全局共享，初值为 1
```

> `n` 从 **1** 起而不是 0。参考源码 `data.js` 里 `buyTimes:1` 并带注释
> 「由于金币计算公式原因（0次和1次购买金额相同），因此此次必须填1」。所以第 1 次购买就是 20 金币。

累计花费有闭式解：

```
cumulativeCost(n) = 10 · n · (n + 1) · (n − 1) / 3 + 20 · n
```

前 18 次：`20, 60, 140, 280, 500, 820, 1260, 1840, 2580, 3500, 4620, 5960, 7540, 9380, 11500, 13920, 16660, 19740`

### 4.2 收益按楼层分档

```
tierMul = ⌊floorIndex / 10⌋ + 1
增量 = 基础值 × tierMul          基础值：HP 100 / ATK 2 / DEF 4
```

| 楼层 | 倍率 | HP | ATK | DEF |
|---|---|---|---|---|
| 1–9 | ×1 | +100 | +2 | +4 |
| 10–19 | ×2 | +200 | +4 | +8 |
| 20–29 | ×3 | +300 | +6 | +12 |
| 30–39 | ×4 | +400 | +8 | +16 |
| 40–49 | ×5 | +500 | +10 | +20 |
| 50 | ×6 | +600 | +12 | +24 |

### 4.3 核心设计洞察：价格与楼层无关，收益与楼层有关

**价格只与「总购买次数」有关，与在哪一层买无关；而收益随楼层翻倍。**

这直接推出原版的最优策略 —— **前期不买，把钱留到高楼层再买**。
在 1~9 层买一次攻击只 +2，在 40~49 层花同样的钱却 +10。
攻略里那句「1-10层不需进商店买攻防，省钱以后可多买」正是这个数学结论的通俗表达。

> ⚠️ **注意**：参考实现中 `buyTimes` 是**全局变量**，在任何商店购买都会推高后续所有商店的价格。
> 原版各层商店定价是否独立，现有参考资料不足，**本项目暂按「全局共享」建模**
> （`constants.json` 的 `shop.globalCounter = true`）。这一条是待验证项，若找到反例需修正。

### 4.4 经济上限

| 指标 | 值 | 说明 |
|---|---|---|
| 全游戏总金币 | **18145** | 基准帖累计总金币序列末值，各段累计值逐项加和自洽 |
| 全花在属性上，最多购买 | **17 次** | 累计 16660；第 18 次要 19740，已超预算 |

**整局 50 层只有约 17 次属性购买** —— 这就是原版魔塔「极致紧张」的数学根源，也是复刻时必须守住的手感。

### 4.7 原版作者给出的进度检查点

智者的提示里藏着一个**权威的数值基准**（`wiserWord[27]`，第 27 层的智慧老人）：

> 第 27 层应达到：**生命 1500 / 攻击 80 / 防御 98 / 1 把蓝钥匙 / 5 把黄钥匙**，
> 达到即算「前期比较成功」。

这是**原版作者本人给出的设计基准**，比任何事后推算都可靠。可用于校验本项目的数值曲线：
若玩家的实际属性显著偏离这条线，说明数值体系偏了。

同层提示还给出了一条策略建议（`wiserWord[7]`）：
「在商店里你最好选择提升防御，只有在攻击力低于敌人的防御力时才提升攻击力」
—— 这与 §3.5 的「数值门」机制完全呼应：**攻击力只需要刚好越过门槛，其余预算投给防御才划算。**

## 5. 钥匙经济学

**每一区的总钥匙数都小于总门数。** 这不是配平失误，是原版最硬的关卡约束。

| 区域 | 层 | 黄钥匙 / 黄门 | 蓝钥匙 / 蓝门 |
|---|---|---|---|
| 一区 | 1–10 | 60 / 64 | 4 / 5 |
| 二区 | 11–20 | 47 / 58 | 6 / 8 |
| 四区 | 31–40 | 48+3 / 53 | 7 / 9+1 |
| 五区 | 41–49 | 26 / 56 | 6 / 13 |

（基准帖原始数字，带 `+N` 表示「另有 N 个在特定条件下才计入」。三区基准帖未给出钥匙数据。）

本项目实际地图数据的统计结果（由 `tools/validate-data.mjs` 的 F 段输出）：

| 区域 | 黄钥匙/黄门 | 蓝钥匙/蓝门 | 红钥匙/红门 | 怪物金币 |
|---|---|---|---|---|
| 一区 | 56 / 65 | 3 / 6 | 1 / 1 | 611 |
| 二区 | 44 / 58 | 6 / 11 | 1 / 1 | 2352 |
| 三区 | 0 / 0 | 0 / 0 | 0 / 5 | 1022 |
| 四区 | 43 / 60 | 5 / 9 | 1 / 2 | 5904 |
| 五区 | 26 / 56 | 6 / 13 | 1 / 2 | 6953 |
| 顶层 | 0 / 0 | 0 / 0 | 0 / 0 | 5000 |

**全塔钥匙 193 把 vs 门 289 扇（门多 96 扇）。**

> **不要「好心」把钥匙给够。** 必须让玩家面对「这一扇门值不值得开」的判断，这是原版关卡体验的核心。

**已知差异：** 本项目黄钥匙一/二/四区比基准帖少 4~8 把，最大偏差 15.7%。
原因是基准帖的「总黄钥匙」**含商人出售的钥匙**，而商人在地图数据中只是 NPC（`sourceId 33`），不携带钥匙实体。
这是**已知且可解释的差异**，校验器将其降级为警告而非失败。

## 9. 新增内容时的自检清单

新增任何一层或一只怪时，逐条过一遍：

- [ ] `hero.atk > mon.def`？（否则玩家会撞上无解墙，属于设计故意还是失误？）
- [ ] 用**该层的参考属性**算过损失，而不是用怪物的 tier？
- [ ] 带上 traits（领域 / 夹击 / 斩杀）重算，占比是否仍可接受？
- [ ] 这一层的钥匙数 vs 门数，是否**恰好差一点**？（刚好够用会失去张力）
- [ ] 打完这层，玩家剩余 HP 是否足够支撑下一层开局？
- [ ] 金币收益是否被计入 §4.4 的 17 次总预算？（超额会破坏经济紧张感）
- [ ] `node tools/validate-data.mjs` 是否 0 失败？
