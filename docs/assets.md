# 美术素材系统（v0.1）

本文说明 `assets/` 下的素材从哪来、怎么加工、以及运行时怎么用。
授权与逐包署名见 [`assets/ATTRIBUTION.md`](../assets/ATTRIBUTION.md)，
本文只讲工程结构与决策。

---

## 1. 目标与约束

| 目标 | 具体要求 |
|---|---|
| 风格 | 贴近马里奥 / **塞尔达织梦岛** —— 16×16 俯视像素，粗块、高饱和、深描边 |
| 权属 | **必须可商用**，且不触碰任天堂 IP（微信小游戏需软著登记） |
| 多角度 | 人物与怪物等运动物体要有**多方向、多帧**素材 |
| 体积 | 微信小游戏对首包体积敏感，图集要小 |
| 可维护 | 素材加工必须**可重跑**，不许手工修图 |

## 2. 目录结构

```
assets/
├── ATTRIBUTION.md          授权与逐包署名（合规凭据）
├── MANIFEST.json           ★ 实体 → 图集坐标的唯一事实来源（脚本生成，勿手改）
├── raw/                    原始素材，只读。按来源分包归档
│   ├── 0x72/               326 个语义化命名的逐帧 PNG + 完整图集
│   ├── armm-zeldalike/gfx/ 8 张：角色表、NPC 表、三套图块、物件、字体
│   ├── kenney/             tiny-dungeon / tiny-town / roguelike-* / ui-pack / mobile-controls
│   └── tiny-zelder-clone/  备用
├── atlas/                  ★ 运行时实际加载的图集（脚本生成，勿手改）
│   ├── terrain.png  512×49      4.6 KB
│   ├── actors.png   512×134    12.0 KB
│   ├── monsters.png 512×169    18.1 KB
│   └── items.png    512×99      3.5 KB
└── preview/                目视核对图（不参与运行）
    ├── atlas-*.png         各图集的放大对照
    └── mock-board.png      ★ 用 MANIFEST 拼的模拟棋盘
```

**图集总大小 ~38 KB。** 作为参考，这比一张普通的背景图还小，
微信小游戏的分包压力基本可以忽略。

## 3. 选了哪些包，为什么

选型顺序是「先用现成的，找不到才生成」。最终 6 个包里，
**0x72 承担大头，ArMM1998 承担多角度**：

| 需求 | 采用 | 理由 |
|---|---|---|
| 怪物（34 只，要动画） | **0x72** | 25 种生物 ×(idle 4 帧 + run 4 帧)，且**逐帧文件带语义命名**，不用目测切图 |
| 地形（墙/门/地面） | **0x72** | 全套墙体转角/侧边/顶边 + 8 种地面 + 门 + 梯子，是成套系统而非散件 |
| **勇者 / NPC 多角度** | **ArMM1998** | 全项目**唯一**提供「4 方向 × 4 帧走路 + 挥剑」的 CC0 来源 |
| 钥匙 / 盾牌 | **Kenney Tiny Dungeon** | 0x72 没有钥匙与盾，Kenney 有三色钥匙（#126 绿 / #127 红 / #128 蓝）与盾（#102） |
| 界面 / 触屏 | **Kenney** | 现成的 UI 包与虚拟摇杆，留给后续触屏与界面接入 |

### 被排除的候选

- **Ninja Adventure（CC0，内容极全）**：其 GitHub 仓库是 Godot 示例工程，
  **不含角色与怪物美术**（`content/character/` 只有一张 `Shadow.png`），
  完整包在 itch.io 但需交互式下载。**已排除**。
- **itch.io 直连**：测得需经代理，且多数包需要交互才能取到文件，不适合脚本化。
- **Liberated Pixel Cup**：多角度动画最全，但授权是 **CC-BY-SA 3.0 / GPLv3**
  （传染性），且素材为 64×64，与 16×16 基准不匹配。**未采用**。

## 4. 网络取用的实测结论

素材站点在国内的可达性差异极大，直接决定了取用路径。实测数据：

| 通道 | 实测速度 | 结论 |
|---|---|---|
| `kenney.nl` 直连 | ~24 KB/s | 可用，逐个拉 |
| `opengameart.org` 文件 CDN | **2.2 KB/s** | 只适合小文件（171 KB 约 80 秒） |
| `opengameart.org` 网页 | 首页 30 s 超时 | 网页几乎不可浏览 |
| `raw.githubusercontent.com` **直连** | 1.3 KB/s | ⚠️ 直连反而慢 |
| `gh-proxy.com` + GitHub | **94 KB/s** | ★ 快通道，比 OGA 快 40 倍 |
| `ghproxy.net` + GitHub | 19 KB/s | 备选 |
| `itch.io` 直连 | 超时 | 走 `127.0.0.1:7890` 代理可通（3.9 s） |

**结论**：GitHub 上的素材走 `gh-proxy.com` 是最优路径；
OGA 只用来取那一个 171 KB 的 ArMM1998 包。

## 5. 加工流水线

```
tools/build-assets.py            切图 / 调色板变换 / 归一化 / 打包 / 断言
        │
        ├──▶ assets/atlas/*.png        运行时图集
        ├──▶ assets/MANIFEST.json      坐标映射表
        └──▶ assets/preview/atlas-*.png 目视核对

tools/preview-board.py           读 MANIFEST，拼一张模拟棋盘
        └──▶ assets/preview/mock-board.png

assets/preview/                   目视核对（不参与运行）
        ├── atlas-*.png            四张图集的放大对照
        ├── mock-board.png         python 侧拼的模拟棋盘
        ├── before-after-palette.png  地面配色 / 宝石的前后对照（§7 ④⑤）
        └── in-game-*.png          浏览器里真实渲染的截图（棋盘/商人/战斗）
```

重跑：

```bash
npm run assets                    # 等价于 python3 tools/build-assets.py
python3 tools/preview-board.py    # 目视核对用的对照图
```

> 需要 Python 3.8+ 与 Pillow（`python3 -m pip install pillow`）。
> 用虚拟环境时把解释器路径传给 `npm run assets`：`PYTHON=<venv>/bin/python npm run assets`。

> `tools/build-assets.py` 里 `MONSTERS` / `ITEM_SRC` / `TERRAIN` 三张表是
> **唯一的映射事实来源**。要换素材或调颜色，改表后重跑，不要改 `atlas/`。

## 6. 四条关键设计决策

### 6.1 16px 基准 + 2 倍整数放大

棋盘格子是 **32px**（`LAYOUT.board.cell`），素材基准是 **16×16**，
运行时按 **×2 整数倍最近邻**绘制。整数倍是关键：非整数倍会把像素画的
硬边插值成糊边，整套素材的「像素感」当场消失。

「大家伙」用 **×3 = 48px**，溢出格子 8px —— 仍然是整数倍，像素依旧清晰。

### 6.2 怪物靠「调色板变体」成族，而不是逐个重画

34 只怪物的名单本身就成族：

```
skeleton / skeletonSoldier / skeletonCaptain      ← 骨 → 铁甲 → 金甲
juniorMage / seniorMage / juniorWizard / seniorWizard
juniorGuard / midGuard / seniorGuard              ← 青铜 → 白银 → 黄金
greenSlime / redSlime / bigSlime / slimeKing
orc / orcWarrior ·  bat / bigBat / vampireBat ·  knight / knightCaptain / darkKnight
```

**原版 50 层魔塔就是这么做的** —— 同图换色表达三级进阶。这不是偷懒，
是这个品类的既定视觉语言。所以 34 只怪物实际只需要 ~20 个基础造型。

变换分两种，**必须按材质选**：

| 函数 | 适用 | 理由 |
|---|---|---|
| `ramp(im, dark, light)` | 金属 / 骨甲（战士、骑士、骷髅、守卫、石巨人） | **保留明暗结构**，只换材质色。用转色相会把骑士糊成一坨纯色 |
| `hue_shift(im, deg, sat, val)` | 史莱姆、蝙蝠、法师袍 | 这些本来就是单色生物，转色相最自然 |

> ⚠️ **这条规则在 2026-09-22 被部分推翻**：上面的变体只解决「同族进阶」，
> 不解决「名字与素材根本对不上」—— 0x72 包里没有蝙蝠 / 龙 / 乌贼 / 石头人 / 史莱姆，
> 当初是靠 `hue_shift` 把 `swampy`（绿衣人）、`imp`（小恶魔）、`chort`（小鬼）
> 推成这些名字的，画面上是「标着『绿史』却是个拿铲子的绿衣人」。
> 现在这 13 只改成**按名称手绘**，见 §13。
> `hue_shift` 仍用于它擅长的场合（单色生物的同族换色）。

### 6.3 角色精灵「底部居中」对齐

所有角色类素材统一贴到一个底部居中的画布上（`bottom_center()`）。
俯视游戏里精灵必须**脚踩格子下沿**才站得住，居中的话会像浮在半空。
在加工阶段一次性对齐，渲染层就不必为每张图单独调偏移。

### 6.4 归一化：图集里的怪物帧一律 16×16

0x72 里 `ogre` / `big_demon` / `big_zombie` 是 **32×32**（像素密度是别家的两倍）。
如果原样混入，`drawScale=3` 会算成 **96px（整整 3 格）**。
所以构建时强制归一化到 16×16，**落屏尺寸只由 `drawScale` 决定**。

## 7. 构建脚本里的自动断言

配色和一致性不能靠「看着还行」。`build-assets.py` 内置了两组断言，
失败会出现在输出的「需注意」列表里：

**① 地形色彩区间**（`verify_terrain`）

| 地形 | 色相要求 | 明度下限 |
|---|---|---|
| 空地 | 0–48°（暖砂石） | **0.55** |
| 岩浆 | 8–48°（橙红） | 0.30 |
| 黄门 | 32–62° | 0.35 |
| 蓝门 | 190–250° | 0.35 |
| 红门 | 335–360° 或 0–22°（红跨 0°） | 0.35 |

> 这组断言是**踩坑换来的**。最初红门用 `hue_shift(+250°)` 实现，
> 肉眼在缩略图上以为是「转了色」，实测平均色相落在 **250.8°（蓝紫）——
> 门是紫的**；岩浆被转到 **201.6°（青色）**。
> 用色相区间一测就现形。

**② 假墙 ≡ 真墙（逐像素）**

假墙一旦看得出来，这个地形的**玩法就直接失效**。所以构建时断言
两者图像完全一致 —— 这不是审美问题，是正确性问题。

**③ 「大家伙」落屏尺寸一致**

防止体型层级倒挂。这条也来自真实翻车：`big_demon` 原本 32×32，
按 1:1 绘制只有 32px，而 16×16 放大 3 倍的巨龙有 48px ——
**魔王看着比小龙还弱**。

**④ 地面 / 墙的明度比 ≥ 2.0**（`verify_terrain`）

这是后面接入渲染层时才暴露的一条：0x72 的 `floor_1` 与 `wall_mid`
**共用同一套三色** `(72,59,58)/(119,92,85)/(34,34,34)`，源素材根本没打算
靠颜色区分地面和墙。只给地面提亮 ×1.5 时，两者**平均亮度 0.364 vs 0.232，
比值 1.57** —— 迷宫的地面/墙读不出来，整屏糊成一坨褐色；
更糟的是墙的砖缝 `(34,34,34)` 正好等于史莱姆身体的深色，怪物会「粘」在墙上。

改成 `ramp_norm()`（先把亮度拉伸到满量程再映射到暖砂石渐变）后
**0.643 vs 0.232，比值 2.77**。断言卡在 2.0，防止这件事回潮。

> 教训：这类问题在缩略图上**非常容易「看着还行」地蒙混过去**，
> 只有数值能抓住。凡是「靠视觉区分」的东西，都应该有一条数值断言。

**⑤ 宝石必须是菱形且颜色正确**（`verify_items`）

失败模式同样是**静默**的。上一版从 0x72 图集 `r12c1`/`r12c3` 切了两块
**纯色矩形**当红/蓝宝石（那两格其实是图集里给别的用途画的色块），
构建不报错、渲染也不报错，只是棋盘上出现两个莫名其妙的正方形。

现在两条断言一起上：**行宽轮廓**必须是菱形（中间最宽、上下收窄），
**主色相**必须红 ≈0°、蓝 ≈210°。色相用 `dominant_hue()` —— 取「有彩度像素的
颜色众数」而不是均值：像素画的颜色是离散的，均值会把红色（5°）和描边墨色
（312°）平均成 150° 附近的中间色，让判断假通过。

## 8. MANIFEST.json 结构

```jsonc
{
  "meta": { "baseTile": 16, "cell": 32, "drawScale": 2, "bigScale": 3, "atlases": { … } },

  "terrain": {
    "0":  { "atlas": "terrain", "x": 0,  "y": 0, "w": 16, "h": 16, "drawScale": 2,
            "name": "floor", "src": "0x72/floor_1 @ 提亮 ×1.5" },
    "1":  { … },  "1:top": { … },   // 上方无墙时的「顶边」变体
    "11": { … }                     // 假墙：与 "1" 逐像素相同
  },

  "actors": {
    "hero": {
      "src": "ArMM1998 / Zelda-like — character.png",
      "dirOrder": ["down", "left", "up", "right"],
      "walk":   { "down": [ {x,y,w,h,atlas,drawScale} ×4 ], "left": […], … },
      "attack": { … }
    },
    "npcs": { "sage": { "walk": { "down": [ …×4 ], … } }, "merchant": { … } }
  },

  "monsters": {
    "skeleton": {
      "src": "0x72/skelet", "note": "骨色原样", "drawScale": 2,
      "frame": { "w": 16, "h": 16 },
      "idle": [ {x,y,w,h,atlas} ×4 ], "run": [ … ×4 ]
    },
    "未映射的怪": null              // 明确标 null，渲染层据此回退程序化图形
  },

  "items": { "redPotion": { "atlas": "items", "x": …, "src": "0x72/flask_red" } }
}
```

### 动画约定

- 走路是 **4 帧循环**，可直接按 `0→1→2→3` 顺序播放。实测每个方向
  4 帧中**有 3 帧互不相同**，即「3 姿势 + 1 回位」的经典循环结构。
- 每个朝向的帧**互不相同、互不为镜像**（已用逐像素比对确认），
  所以 4 个方向必须各自取图，不能靠水平翻转省素材。

## 9. 覆盖情况

| 类别 | 覆盖 |
|---|---|
| 地形 | **13/13**（12 种地形 + 1 个墙顶边变体） |
| 怪物 | **34/34** 数据中的怪物全部有素材（另有 2 只备用：goblin、ice_zombie） |
| 道具 | **32/32** |
| 勇者 | 4 向 × 4 帧走路 + **4 向 × 4 帧挥剑** |
| NPC | **6 人 × 4 向 × 4 帧**（16×26 程序化像素画，**本项目自绘** —— 见 §9.1） |

**零缺口。** 渲染层目前不需要走程序化兜底。

### 9.1 NPC 为什么从「取素材」改成了「自己画」

第三方免费素材包里**只有一个 NPC 角色**（`NPC_test.png`）。最初六个职能
（智者 / 商人 / 商店 / 小偷 / 仙子 / 公主）共用这一张图 —— 结果是「不同功能的
NPC 长得一模一样」，地图上根本分不出谁是卖东西的、谁是给情报的。

素材库里也没有第二套可用的多角色 NPC 集，于是改为在
`tools/build-assets.py` 里用 `_put()` 一个原语手绘五行像素块。六个职能各一组
造型参数（`NPC_ART`），靠**剪影 + 帽子 + 手持物**区分：

| 职能 | 剪影记号 | 手持物 |
|---|---|---|
| `sage` 指引 | 灰白长袍 + 尖顶软帽 + 白须 | 法杖（顶端宝石） |
| `merchant` 交易 | 暖褐短袍 + 宽檐帽 | 腰侧钱袋 |
| `shop` 属性 | 深绿外袍 + 皮围裙 | 手边一摞金币 |
| `thief` 情报 | 兜帽 + 蒙面（只留眼缝） | 腰侧短匕 |
| `fairy` 祝福 | 青白长裙 + 背后薄翅 | 星杖 |
| `princess` 主线 | 粉裙 + 长发 + 金冠 | —— |

生产端的两条断言（`verify_npc_art()`，跑在构建里，不看图也能拦住回归）：

1. **六个剪影必须互不相同** —— 用 alpha 通道逐像素比对。这条针对的正是
   「改回共用一张图」这种退化（那种情况下画面照旧，只是又变回六个人一个样）。
2. **脚必须踩到最底行** —— 精灵是底部锚定的（`anchor.set(0.5, 1)`），
   素材里若留了空行，人就会浮在半空。

配色与 `src/render/theme.ts` 的 `NPC_ROLE` 一一对应，同一职能在整座塔里颜色恒定；
渲染层另有 4 帧呼吸动画（头与躯干上移 1px、下摆与脚不动）。

> ⚠️ **6 套造型里有 2 套在游戏里见不到**：`thief`(34) 与 `fairy`(35) 这两个职能
> 在参考源的地图里**从未被放置**（role 层只用了 32/33/36/39）。造型、职能色、
> 台词都已就绪，缺的是地图数据 —— 这是参考源自身的不完整，
> `npm run validate` 的 I 段每次都会报告，详见 `docs/known-gaps.md`。

## 10. 关于「生成」的比例

用户的要求是「优先用现成的，没有合适的再生成」。实际执行结果：

| 来源 | 数量 | 说明 |
|---|---|---|
| 0x72 直接取用 | 10 项道具 + 全部地形 + 23/36 只怪物 | 药水、剑、金币堆 |
| Kenney 取用 | 9 项 | 三色钥匙、五级盾牌 |
| 0x72 图集内切取 | 1 项 | 镐（`frames/` 里没有） |
| **程序化生成** | **12 项** | 见下 |
| **合计** | **32 项，生成占比 37.5%** | |

生成的 12 项：炸弹、十字架、雪球、地震卷轴、镜翼、上飞翼、下飞翼、
传送阵、怪物图鉴、笔记本、**红宝石、蓝宝石** —— 这些在六个免费包里
**确实找不到对等物件**。由 `build-assets.py` 的 `gen_icon()` 绘制，
每张都过一道 `add_outline()`，保证和手绘素材一样带深色描边，
混在一起不会露馅。

> 宝石原本试图从 0x72 图集切（`frames/` 里确实没有），但切到的是两块
> **纯色矩形**，棋盘上就是两个方块。核对过 0x72 全部 130 张帧
> （只有 `skull` / `coin` / `flask_*` / `ui_heart_*`）和 Kenney 的
> `roguelike-rpg-pack` / `tiny-dungeon`（没有红/蓝菱形）之后，
> 才确认这是**真的缺**，于是生成。见 §7 第 ⑤ 条断言。

**怪物：13 只手绘 / 23 只取素材。** 全塔 36 只里，23 只由 0x72 的角色底图
按调色板变换得到（`ramp` 保留明暗结构 / `hue_shift` 换色）；另外 13 只
**名字与素材根本对不上**，已改成按名称手绘（史莱姆族 4、蝙蝠族 3、
石人 / 乌贼 / 龙 / 吸血鬼 / 魔王 2），见 §13。

## 12. 塔壁平铺地图内墙贴图（同源，不是调色）

棋盘外围那圈「塔壁」原本是一组**自绘的冷灰蓝**（`#8b98ac`），而地图内部是暖褐石墙
（墙贴图 `#433836`，亮部 `#775c55`）—— 冷暖两套色系撞在一起，一眼就看出「周边是后期贴上去的」。

调色对齐是治不住的（两套色系的中间值是脏的），所以改成**平铺同一张贴图**：
`board.ts` 的 `buildParapet()` 直接取 `atlas.terrain('1')` 的 `source.uid`
—— 与地图内墙**同一个来源**，结构上就不可能不一致。

| 手法 | 为什么 |
|---|---|
| 平铺地图内墙贴图 | 同源 → 色相 / 砖缝 / 亮暗关系全部自动一致，换素材也不会漂 |
| `Container.mask`（Graphics 圆角矩形）裁切 | 平铺是矩形铺满，塔壁要圆角；遮罩裁出圆角 |
| 城垛与外缘描边**画在 `wall` 容器之外** | 否则会被遮罩一起裁平（这是本轮踩到的实际坑） |
| 城垛凹口**不画** | 让星空从缺口透出来，是「位面可见」的一处细节 |

`theme.ts` 另留一组 `STONE` 石材令牌，取自那张贴图的实际像素色，
给**不贴图也要有颜色**的地方用（棋盘底板、塔壁内缘阴影、外缘描边）：

| 令牌 | 值 | 取自贴图哪里 |
|---|---|---|
| `face` | `#7a5c4e` | 墙身主体（亮部 `#775c55` 往暖里推一档） |
| `faceLit` | `#9a7a68` | 受光面（城垛顶、砖面上沿） |
| `faceDark` | `#503c34` | 背光面（砖面下沿、石基）—— 棋盘底板用它 |
| `joint` | `#2a201c` | 砖缝 |
| `top` | `#b08e78` | 城垛顶面（朝天，最亮） |
| `inner` | `#1f1815` | 贴着棋盘那一圈的内阴影：让地图**嵌**进塔壁里，而不是浮在墙上 |
| `edge` | `#120d0b` | 塔壁外缘描边（与夜色交界） |

**回归保护（`verify-visual.cjs` 的 A9）**：断言 `__wallSources()` 里
`parapet === inner`（比 `source.uid`，不是比颜色）。比 uid 的好处是
「以后换贴图 / 又加一层自绘颜色叠加」也会立刻红 —— 颜色可以蒙对，uid 蒙不过去。
另有像素核对：截图里塔壁与地图内墙的色相差实测 **15°**、`R > B`（暖色）。

> 素材侧无需任何改动：塔壁用的是**已有的**地形墙贴图，没有新增图片，
> 也没有进 `MANIFEST.json`。改的只是「谁在用它」。

## 13. 按名称程序化重绘：13 只与名字不符的怪物

起因是一句反馈：**「怪物模型优化要更符合怪物名称」**。

### 13.1 为什么换素材解决不了

先做的是**调查能不能换素材**，结论是不能：

0x72 地牢包一共 24 张角色底图（`skelet` / `knight` / `imp` / `swampy` / `chort` /
`ogre` / `wizzard_*` / `orc_*` / `big_demon` …），**全部都是人形**。
包里**没有**蝙蝠、龙、乌贼、石头人、史莱姆、吸血鬼。
备选包（Kenney `roguelike-characters` 等）也只有人形与四足动物，没有能塞进
16px 像素画风格的非人形。

于是第一版只能「硬凑」——用一个人形去顶一个不是人的名字：

| 怪物 | 旧素材（0x72） | 问题 | 现在 |
|---|---|---|---|
| `bat` / `bigBat` / `vampireBat` | `imp`（有角的小恶魔） | 是小恶魔，不是蝙蝠 | 尖耳 + 展开的膜翼（窄翼 / 宽翼 / 宽翼 + 獠牙） |
| `greenSlime` / `redSlime` / `bigSlime` / `slimeKing` | `swampy` / `muddy`（穿绿衣的小人） | **「绿史」是个拿铲子的绿衣人** | 圆顶果冻；「大」用体量表达、「王」加三尖金冠 |
| `stoneGolem` | `ogre`（食人魔） | 是个胖人形 | 方块躯干 + 砖缝 + 发光眼，全程只有直角 |
| `kraken` | `swampy`（绿衣人形） | 完全不搭 | 宽圆头 + 侧鳍 + 六条**向外张开**的腕 |
| `dragon` | `chort`（小鬼） | 拿小鬼当魔龙 | **侧视**：角 + 长吻 + 背上的翼 + 尾 + 两条腿 |
| `vampire` | `zombie` 换紫 | 人形，但毫无吸血鬼特征 | 高领斗篷 + 獠牙 + 红眼 |
| `demonKing` / `demonKingTrue` | `big_demon`（32×32 归一化到 16） | 归一化丢像素，糊 | 巨角 + 膜翼 + 发光眼；真身换猩红 + 金冠 |

`MONSTERS` 表里**源名写 `"gen"`** 就是「这只不取 0x72，按名称手绘」。
最终：**36 只 = 23 只取素材 + 13 只手绘（7 种形状）**。

### 13.2 两条实现路线：算出来的 vs 画出来的

照搬 §9.1 的 NPC 做法（`_put()` 一个原语填像素块，硬边、不是矢量缩放），
但按「形状是被算出来的还是被画出来的」分成两条路：

| 形状 | 用在哪 | 路线 |
|---|---|---|
| `slime` | 史莱姆族 ×4 | **算**：半宽逐行 +1 做圆顶，`top` 越小越「大只」 |
| `kraken` | 大乌贼 | **算**：六条腕按 `dir` 每行向外挪 1px —— 「张开」才是乌贼 |
| `golem` | 石头人 | **算**：全程直角，和生物形成对比 |
| `vampire` | 吸血鬼 | **算**：高领 + 露手，靠剪影表达「斗篷」 |
| `demon` | 魔王 ×2 | **算**：`_sym()` 镜像成对结构，保证两只角不差 1px |
| `bat` | 蝙蝠族 ×3 | **画**：模板 `BAT_NARROW` / `BAT_WIDE` |
| `dragon` | 魔龙 | **画**：模板 `DRAGON_ROWS`（侧视） |

形状与颜色分开：`PROC_MONSTERS` 里只写颜色，形状函数不关心自己代表谁。
史莱姆族四只是同一个形状、四套颜色（绿 / 红 / 更大 / 金冠）。

### 13.3 一条必须先记住的约束：`add_outline` 是 1px 八邻域膨胀

生成完一律过一道 `add_outline()` 补深色描边（和素材包里的原件一致）。
但它是**膨胀**，这带来一个反直觉的后果：

> **1~2 列宽的缺口会被描边填满。** 想把两块真正分开，缝至少要留 3 列
> （缝会被左右各吃掉 1 列）。

所以「腿之间留几列」「翼和身体怎么分开」不是审美问题，是被这条规则卡死的。
反过来利用它：**想要一条可见的分缝线，就故意留 1~2 列缺口** ——
描边会把它变成一条深色线，正好当「翼指分叉」。

### 13.4 教训：手写坐标会把形状藏起来（蝙蝠画成了「锚」）

第一版 `_mon_bat` 把翼写成「每行一段 `(x, y, w)`」，八行都写成了满宽。
渲染出来逐行量宽度是：

```
6 6 12 14 16 16 16 16 16 16 4 4 6 6 6     ← 旧版：8 行满幅 + 4px 细杆
```

宽横梁 + 细杆 + 底座 —— **这是一个「锚」**。

最要命的地方不是画错了，而是**看不出来**：坐标是数字，读代码读不出形状，
而当时看不了图，于是这版差点就这么交出去。

修法不只是改数字，而是**换表现方式**：`bat` / `dragon` 改用**字符模板**
（`_stamp(rows, legend)`），把形状直接画在源码里：

```python
BAT_NARROW = [
    "......m..m......",   # 尖耳
    "......ibbi......",   # 眼
    "...MMmbbbbmMM...",   # 翼（M 受光 / m 膜）
    "MMMmmmbbbbmmmMMM",   # 翼最宽的一行
    "......bbbb......",   # 垂在下面的身体
    ".....bbbbbb.....",   # 脚
]
```

可读、可 review、可 diff，改一列就是改一个字符；`_stamp` 对**行列长度**做断言，
「多写少写一个点」在构建时就报错。
蝙蝠的剪影从此是「窄 → 宽 → 窄」的**腰鼓**：

```
6 6 10 12 16 16 16 16 14 12 10 6 6 8 8 8
```

### 13.5 教训二：翼 / 尾 / 腿不能共用一个颜色

旧版 `dragon` 的翼膜、尾巴、腿全用 `dark`，结果右侧与下方连成一整团黑红 ——
**剪影退化成一整块砖**。现在拆成四个色：`body`（红身）/ `belly`（亮腹甲）/
`wing`（暗栗膜）/ `dark`（近黑腿与尾），四个块才分得开。

### 13.6 怎么看：量剪影，别「看图」

看不了图的时候（这次的处境），唯一可靠的验证是把每个形状的 **alpha 通道导成
ASCII 廓形 + 逐行宽度序列**，对着**宽度序列**判断，而不是对着颜色判断：

| 形状 | 剪影应长成 |
|---|---|
| 蝙蝠 | 腰鼓（窄→宽→窄）；出现连续 6~8 行满幅 = 已退化成「锚 / 砖」 |
| 史莱姆 | 上窄下宽的圆顶，底部两行压暗 |
| 石头人 | 全直角，肩比腰宽 |
| 龙 | 四个记号分居四个方向（角在上 / 头在左 / 翼在右上 / 尾在右） |

好处是颜色、光照、缩放都不影响判断 —— **只有形状在说话**，
而这恰好是这一轮唯一要改的东西。

### 13.7 生产端断言（`build-assets.py`）

| 断言 | 抓什么 |
|---|---|
| `_stamp` 行列长度 | 模板多写/少写一个点 |
| `verify_mon_art` ① | **每种形状的剪影互不相同** —— 抓「画了半天结果都是同一个圆」 |
| `verify_mon_art` ② | **同形状的变体必须逐像素不同** —— 抓「换色没生效 / 两只一模一样」 |
| `verify_mon_art` ③ | 底行必须有像素 —— 底部锚定下帧底留白 = 怪物浮在半空 |
| `verify_mon_art` ④ | 每个形状至少有一只怪在用 —— 抓「画了却忘了接进 `PROC_MONSTERS`」 |
| `MONSTERS` ↔ `PROC_MONSTERS` 双向对账 | 声明 `gen` 的与实际画出来的不一致（两边都是漏网的入口） |

### 13.8 运行时断言（`verify-visual.cjs` 的 A12）

生产端对了，不代表**落屏**是对的 —— 渲染层是「有图集用图集，没有就退回
`icons.ts` 的程序化图形」，一旦退回，这一轮就等于白做，而画面看上去「还好」。

所以新增 `board.__sprites()`：把棋子上**真正落屏**的精灵报出来
（`source.uid` + 帧矩形），与 `MANIFEST.json` 的 `idle` 帧对撞：

| 判据 | 说明 |
|---|---|
| 没有**任何**怪物 `uid === null` | null = 走了程序化兜底 |
| 全部怪物共用同一个 `source` | 怪物只有一张 `monsters.png` |
| 落屏帧矩形 ∈ 该怪的 `idle` 四帧，且 16×16 | `idle[0]` 会假红 —— 按相位取帧，见下 |
| 这 6 层里该出现的手绘怪物一只不少 | 抓「改完忘了接进去」 |

> 这条断言第一版是**红的**，而且红得有价值：它报出「第 1 层 `greenSlime`
> 落屏 `{x:391}` 而 MANIFEST 是 `{x:340}`」。真因是渲染层按相位在 `idle`
> 四帧间换帧，所以拍到的不是 `idle[0]` —— **期望值写错了，不是实现错了**。
> 改成「必须是 idle 四帧中的某一帧」后转绿，同时把「确实在用图集」这件事
> 钉得更死（连动画帧都覆盖了）。
> 一条断言第一次红，先怀疑期望值 —— 这次就是。

### 13.9 诚实说明：有 2 只做了却看不到
