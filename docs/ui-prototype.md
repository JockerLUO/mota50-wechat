# 原型界面说明（v0.1）

> 目标：**验证数据层能不能驱动一个真实可玩的界面**，并把「数值体系」的价值直接呈现在玩家眼前。
> 不追求美术完成度，但要求交互链路真的接通规则引擎 —— 不是画一堆假格子。

本文记录**已经实现的东西**与**为什么这么写**。待办在最后一节。

---

## 1. 技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| 渲染 | **PixiJS 8.21** | 上一轮已定；WebGL 批渲染，微信小游戏有官方适配层 |
| 构建 | **Vite 6** | HMR 快；原生支持 JSON 导入与 `import.meta.glob` |
| 语言 | **TypeScript 5.9**（`strict`） | 51 层 × 34 怪 × 32 道具的数据结构，靠类型挡住低级错误 |
| 类型检查 | `tsc --noEmit` | 构建前置，`npm run build` 会先跑 |

**UI 全部画在 canvas 上，不用 DOM。** 这是刻意的：目标平台是微信小游戏，那里没有 DOM，
原型阶段就用 canvas 做 UI，可以避免上线前整体重写一遍 HUD。

## 2. 目录与职责边界

```
index.html
vite.config.ts            base './'，host 固定 localhost
src/
  main.ts                 引导 + 失败兜底
  style.css               只负责「铺满窗口」，不含任何 UI 样式
  data.ts                 数据加载与类型（唯一的数据入口）
  game/
    state.ts              GameState 定义 + 网格查询helper
    engine.ts             规则引擎：step / useItem / previewBattle / travelTo / buyStat
  render/
    theme.ts              配色令牌（单一来源）
    icons.ts              程序化矢量图形：地形 / 怪物 / 道具 / 勇者
    board.ts              11×11 棋盘（地形层/实体层/勇者层/浮层）
    hud.ts                状态栏 / 详情卡 / 道具栏 / 消息条 / 楼层面板 / 工具栏（常驻信息）
    trade.ts              商人交易面板 / 商店三选一面板（模态浮层）
  app.ts                  输入分发、自动寻路、主循环
```

**调用方向是单向的**：`app.ts` → `game/` → `core/`，`render/` 只被 `app.ts` 调用，
且 `render/` 里没有任何规则判断（它只问 `engine` 要结论，比如 `previewBattle().grade`）。

`core/combat.mjs` 与 `core/shop.mjs` 是**纯 JS**，Node 校验器和浏览器共用同一份实现 ——
所以战斗公式在「校验台」「校验器」「游戏界面」三处不可能不一致。

## 3. 数据零拷贝

`src/data.ts` 用两条路径直接读仓库根的原始数据，**不做任何拷贝或转写**：

```ts
import tilesJson from '../data/tiles.json';                       // 静态导入
const floorModules = import.meta.glob('../data/floors/*.json', {   // 全量预载
  eager: true, import: 'default'
});
```

这样从根上排除了「内联副本与数据源漂移」—— 这正是前几轮反复出现的 bug 类型。

> ⚠️ **上线前要改**：当前 51 层 JSON 全部进主包（主包 439 KB / gzip 135 KB）。
> 微信小游戏主包 4 MB 够用，但应按需加载或放分包，见 `docs/data-spec.md` 的体积预算。

## 4. 运行时状态设计

`GameState` 是**可序列化的单一状态树**，两条关键设计：

### 4.1 地图数据不可变 —— 改变只记 `terrainPatch`

开门、挖墙、地震卷轴清场……这些都会改变地形，但**绝不回写 `data/`**：

```ts
terrainPatch: Record<number, Record<string, string>>   // 楼层 → "x,y" → 新字符
```

所有规则判定与渲染都走同一个 `tileAt(state, data, floor, x, y)`，
它先查覆盖层再回落原始数据。**只有一个取地形的入口**，就不会出现
「画面是空地、逻辑上还是门」这类撕裂。

### 4.2 实体移除只记 key

```ts
removed: Set<string>   // `floor:x:y:type:id`
```

反复上下楼时怪物不会复活，也不需要深拷贝 51 层数据。

## 5. 渲染层

### 5.1 分层与重建策略

| 层 | 重建时机 |
|---|---|
| 场景背景层（`Backdrop`） | **只在楼层变化且跨过重绘判定时**重画（`setFloor` 先比 `floorShown`，同层直接 return） |
| 地形层（121 个 Graphics） | 只在**该格地形变化**时重画（逐格比对缓存字符） |
| 实体层 | 换层、或实体被拾取/击杀时 |
| 勇者层 | 每步移动做 130ms 三次缓出插值 |
| 浮层 | 每帧重画（只有 2 个描边框，成本可忽略） |

### 5.2 程序化图形，零美术资源

没有一张图片。地形、34 只怪物、32 项道具、勇者全部用 `Graphics` 画出来：

- **怪物按家族给形状**：史莱姆=blob、蝙蝠=双翼、亡灵=骷髅、法师=菱形、卫兵=六边形、
  骑士/兽人=盾形、石头人=方块、乌贼/魔王=触手。再叠 2 字缩写（`绿史`/`骷士`/`骷队`）。
- **道具按类别给形状**：钥匙 / 宝石 / 药瓶 / 剑 / 盾 / 金币 / 书 / 翼 / 炸弹 / 十字 / 雪花 / 锹 / 卷轴 / 传送门。

好处：不用打包图集就能跑；换配色只改 `theme.ts`；不会出现「图集里找不到某格」的运行时惊喜。

### 5.3 怪物角上的「可行性指示灯」

每只怪物右上角一个小圆点，颜色**直接来自 `core/combat.mjs` 的 `grade()`**：

| 颜色 | 含义 |
|---|---|
| 金 | 一击必杀（零损失） |
| 绿 | 轻松 / 可接受 |
| 橙 | 损失偏大 |
| 红 | 危险 / 必死 |
| 紫 | 打不动（ATK ≤ 怪物 DEF） |

原版的「数值门」体验靠玩家心算；这里把它变成**一眼可见**的信息。
这是数值体系对 UI 最直接的贡献，也是本原型最值得保留的设计。

### 5.4 版式与缩放

固定设计尺寸 **420×780**（手机竖屏），运行时按 `min(w/420, h/780)` 整体缩放居中 ——
微信小游戏的标准做法。设计稿坐标写死在 `LAYOUT` 常量里，改版式只改一处。

> 本轮把「同一种风格」也做成了常量：圆角/描边/内边距/字号阶梯/短条/标题落点
> 集中在 `theme.ts` 的 `UI` 令牌里，并加了一条会红的断言（A7）。详见 §14。

## 6. 已实现的交互

| 操作 | 行为 |
|---|---|
| 方向键 / WASD | 走一步；撞怪物=攻击，撞门=用钥匙，撞道具=拾取，撞 NPC=对话（不位移） |
| 点击地图 | **BFS 自动寻路**走过去；中途遇怪物/门/NPC 就停下，把决定权交回玩家 |
| 点击未直入的格 | 目标不可直入（门/墙/岩浆）时，退化成「走到它旁边再撞一下」 |
| 悬停任意格 | 详情卡显示：怪物数值 + **完整战斗预判**、道具效果、NPC 本层商品、地形说明 |
| 点击道具栏 | 使用道具（楼层传送器 / 金钥匙 / 铁锹 / 地震卷轴 / 雪花 / 炸弹 / 上下飞行器…） |
| 「楼层浏览」 | 浏览全部 51 层。HUD 会标明「浏览中（勇者在 N 层）」，勇者定位框隐藏 |
| 「编辑视图」 | 显示埋在墙内的隐藏道具（第 14 层红钥匙、第 41 层下楼器等） |
| **撞商人**（2/6/7/12/15/28/29/31/38/39/45/47 层） | 打开**交易面板**：购买钥匙 / 回收钥匙 / 固定价兑换属性 / 领取一次性剧情赠礼 |
| **撞商店**（4/12/32/46 层） | 打开**三选一面板**：生命 / 攻击 / 防御，同时显示单价、每点成本、买后数值 |
| Esc / Tab / R | 关闭面板 / 切换楼层面板 / 重开（浮层打开时 Esc 优先关浮层） |

**规则实现都标了源码出处**，例如：

- 开门：撞门成功即消耗钥匙并**走上该格**（`event.js:386` 清门后 `player.x++`）
- 假墙：撞一次变空地并走上去（`event.js:412`）
- 对称飞行器：0 基下目标是 `(10−x, 10−y)`（源码 1 基写 `12 - player.x`）
- 楼层传送器：只能去 `visited` 里的层 —— **回溯工具，不能向上推进**
- 战斗前拦截致命损失（原版行为），但**巫师领域扣血可以真的把勇者打死** → 有阵亡界面

## 7. 运行

```bash
npm install
npm run dev        # 开发服务器 http://localhost:5173
npm run build      # tsc --noEmit && vite build
npm run preview    # 预览构建产物 http://localhost:4173
```

`npm run validate` / `npm run import` / `npm run balance` 是数据层脚本（与本 UI 无关）。

调试钩子（浏览器控制台）：

```js
mota.game.__probe()          // 引擎真值快照，用于判断「画面是否只是看起来对」
mota.game.__grant('floorTeleporter')   // 直接发道具，跳过钥匙经济
```

`__grant` 存在的理由：51 层塔里很多道具在钥匙经济上本来就够不着
（例如第 1 层的楼层传送器在 (1,10)，而第 1 层 7 扇黄门只有 5 把钥匙），
要验证某个 UI 状态，靠走位过去不现实。

## 8. 本轮踩到的坑（都已在代码注释里标注）

| 现象 | 真因 | 处理 |
|---|---|---|
| 画面只占左上角 1/4，且像被压扁 | **Pixi v8 的 `renderer.width` 已经是逻辑像素**（内部已除以 resolution），我又除了一次 → 缩放算成 `1/dpr` | 不再除；注释写明 |
| 启动即崩：`object is not iterable` | `constants.json` 的 `regions` 是**说明对象**（`{note: "见 zoneBaseline.regions"}`），不是数组；我按数组 `for...of` 它 | 真区域表在 `zoneBaseline.regions`；类型里写明这个陷阱 |
| 「楼层浏览」切层后画面立刻弹回第 1 层 | `Board.refresh` 用了 `state.floor`，而浏览模式下显示层 ≠ 勇者层；`sync()` 一调就被拽回去 | 改用 `this.floorShown`，并引出 `app.displayFloor` 概念 |
| 浏览别的层时 HUD 仍写「第 1 层」、勇者框还在画 | 状态栏与浮层都只认 `state.floor` | `StatusBar.update` 增加 `shownFloor/browsing` 参数 |
| 打开门后**数据校验报 1 项失败** | 我先改了 `constants.json.hero`，但 `tools/balance-check.html` 的内联副本还没重建 → **防漂移检查正常工作**，抓到的是我自己 | 重建校验台即恢复；同时把该检查收窄为「只比会影响计算的字段」，避免纯文档字段误报 |
| 同文件的多处编辑丢改动 | 同一文件的两处 Edit 放在一条消息里会互相覆盖 | 统一改用**带命中次数断言**的补丁脚本；这条已在 `legacy-game-data-port` 技能里 |
| 交易面板「打开了」却一片空白，而且点不动 | `ModalShell` 构造时把自己设成 `visible = false`，之后再没人打开过它。**Pixi 的命中测试第一步就按 `!visible` 剪掉整棵子树** —— 面板看着"开着"，其实既画不出也点不到 | 可见性统一由外层面板控制，外壳不碰 `visible` |
| 面板第一次打开正常，第二次起全空 | 外壳的 `clearBody()` 顺手 `destroy` 了面板自己持有的 `rowLayer`，之后所有行都加在一个已脱离场景树的容器上 | 外壳**只脱离、不销毁**（内容所有权归子类）；`open()` 里显式把 `rowLayer` 接回 `body` |
| HUD 在没有商店的层提示「商店第 N 次…」 | 详情卡按"当前层所属档位"算价，但全塔只有 4/12/32/46 层真的摆了商店。第 6 层只有商人，提示却让玩家去找商店 | 新增 `hasNpcOnFloor()`，只在真有商店的层显示；措辞改为「本层商店」。状态栏的「商店收益 ×N」同步改为「收益档位 ×N」 |
| 渲染层里藏着一份内联的商店价格公式 | `hud.ts` 直接写了 `10 * n * (n - 1) + 20`，与 `core/shop.mjs` 重复 | 改为直接引用 `core/shop.mjs` 的 `shopCost / shopGain` |

| 钩子 | 作用 |

## 13. 交易界面（商人 / 商店）

### 13.1 一条必须守住的边界：两个「买属性」不是一回事

这是本轮最容易写错的地方 —— 全塔**有两处能买属性，定价机制完全不同**：

| | 商店（`sourceId 39`，4/12/32/46 层） | 商人（`sourceId 33`，仅第 45 层卖属性） |
|---|---|---|
| 定价 | **递增**：`10·n·(n−1) + 20`，n 为全局购买次数 | **固定**：数据里写死的 1000 金币 |
| 增量 | 随楼层档位放大（×1 ~ ×6），见 `constants.shop.tiers` | 数据里写死的 +2000 生命 |
| 是否推进 `buyTimes` | **是** —— 任何商店购买都会推高后续所有商店的价格 | **否** |
| 公式出处 | `core/shop.mjs` | `data/npcs.json` |

混起来的后果很具体：如果第 45 层那次固定价购买也去推 `buyTimes`，
玩家在 4 层商店买到的价格就会莫名上涨。UI 上用「固定价，不涨价」直说了这件事，
测试里也有一条断言专门守它（`**未推进商店购买次数**`）。

> ⚠️ **一处数据推断，需人工确认**：45 层商人可重复购买、且不推进 `buyTimes`
> 是**根据现有数据的推断**（数据只给了固定 price/value，没给限购次数）。
> 原版这里是否限购一次、或是否也参与涨价，参考资料不足。见 `docs/known-gaps.md`。

### 13.2 报价由引擎算，UI 只负责画

面板**不重算价格、也不自己判断能不能买**：

```ts
// engine.ts                      // trade.ts
merchantOffers(state, data, floor) → MerchantOffer[]   // blocked: string | null
shopOptions(state, data)           → ShopView          // affordable / cost / gain
```

判断结果以 `blocked` / `affordable` 字段交给 UI。理由：商店定价同时被
**Node 校验台**和**浏览器**引用（`core/shop.mjs`），UI 再算一遍就等于引入第三个实现。

### 13.3 四种交易算子

`data/npcs.json` 的 `goodsByFloor` 里实际出现了四类条目，全部落地：

| op | 出现位置 | 语义 |
|---|---|---|
| `buyItem` | 6/7/12/15/29/31/38/39/47 层 | 花金币买钥匙或道具 |
| `sellItem` | **仅 28 层** | **反向**：玩家交出黄钥匙换金币（每把 100） |
| `buyStat` | **仅 45 层** | 固定价换属性 |
| `gifts` | **仅 2 层** | 一次性剧情赠礼（金币 +1000），用 `state.claimed` 记「已领取」 |

`gifts` 单独放在 `goodsByFloor[floor].gifts` 而不是 `goods` 里，所以它**不占商品位**、
且用一个 `gift:merchant:{floor}:{index}` 的 key 保证只发一次。

### 13.4 发放 / 扣除道具只有一条路径

拾取和商人买卖共用 `grantItem() / takeItem()`：

```
钥匙（yellowKey / blueKey / redKey） → 进 state.keys，不占背包
可使用（quakeScroll / bomb / 飞行器…） → 进 state.bag，**不立刻结算**
拾取即生效 / 持有即生效（宝石 / 剑盾 / 十字架） → 立刻 applyEffects + 登记 passives
```

分成两处写的话，迟早会出现「地上捡的蓝钥匙进背包、买来的进 keys」这种撕裂。
`quakeScroll` 必须走「可使用」分支 —— 否则买入当天就把本层地图清了。

### 13.5 商店面板刻意摆出来的三个数字

原版商店的核心决策是「现在买还是留钱到高层买」。面板把做这个判断需要的全部数据都摆在明面：

- **单价**（只随购买次数涨）
- **每点属性多少金币**（`cost / gain`，越小越划算）
- **买后数值**（`生命 1100 → 1200`）

再加底部一句策略提示。第 1–9 层的提示直接点明：
> 收益只有 ×1。价格与楼层无关、只随购买次数上涨 —— 现在买是用最贵的钱换最少的属性，
> 原版攻略「1–10 层不进商店」正是这个结论。

### 13.6 交易后必须整块重画面板

成交会同时改变：金币、持有量、以及**每一条的 `blocked`**（买完蓝钥匙后另外几条可能变成买得起或买不起）。
所以 `onTrade` / `onShopBuy` 的收尾动作是「重新拉一次报价 → 往面板里灌」，而不是局部改一个数字。

## 14. 统一版式：从「长得像」到「只有一套数」

本轮的反馈原话是「游戏界面和玩家状态栏 UI 优化，改为同一种风格」。
问题不在某一块面板难看，而在**同一屏里同时存在两套版式**：

| 位置 | 改前 | 改后 |
|---|---|---|
| 状态栏 / 详情卡 / 道具栏 | 各自写圆角（16 / 12 / 10 混用）、各自写内边距 | 全部走 `panel()` + `UI` 令牌 |
| 交易浮层（商人 / 商店） | `card()` 底板 + 一排裸标题 + 蓝色「关闭」 | 短条 + 大标题 + 职能章 + 分隔线，与对话框同源 |
| 按钮 | 胶囊（`h/2`）与方角混用 | 一律 `UI.radiusInner` 方角圆角 |
| 面板标题落点 | `+UI.pad`(14) 与 `+accent.x+accent.w+8`(23) 两种横向混用 | `UI.titleX` / `UI.titleYTitle` / `UI.titleYHead` |

### 14.1 令牌在哪，为什么是这几个数

`src/render/theme.ts`：

| 令牌 | 值 | 说明 |
|---|---|---|
| `UI.radius` | 14 | 面板圆角 |
| `UI.radiusInner` | 10 | 面板内小控件（槽位 / 按钮 / 条） |
| `UI.border` | 1 | 描边宽度 |
| `UI.pad` | 14 | 面板内边距 |
| `UI.accent` | `3×16 @ (12,14)` | 左上角主题色短条 |
| `UI.shadow` | 三层 1~3px 偏移 | 用圆角块伪装投影（Pixi 核心没有投影滤镜，小游戏端不装滤镜） |
| `UI.fs` | 22 / 15 / 12.5 / 11.5 / 10.5 / 14 | 字号阶梯，不许出现 12 / 12.5 / 13 这种看不出差别的存在 |
| `UI.titleX` | 23 | 标题横向 = 短条右缘 + 8 |
| `UI.titleYTitle` / `UI.titleYHead` | 12 / 14 | 大标题 / 小标题各自垂直居中于短条 |

短条是**唯一的花哨元素**，用颜色给面板分职责：状态=蓝（`ACCENT.status`）、
详情=灰、道具=金、NPC 对话与交易=**该 NPC 的职能色**。

### 14.2 一条容易被忽略的真实缺陷

改版过程中量到一个只看源码发现不了的错：交易浮层的标题横向用了 `+UI.pad`(14)，
而短条占 `12..15` —— **标题压在自己的短条上**。差 1px，截图上看不出来，
但同一时刻另外五块面板用的是 +23，「两套版式」看得出来、说不清在哪。
这类问题靠眼看是抓不住的，所以有了 A7。

### 14.3 A7：让「同一种风格」变成一条会红的断言

```bash
npm run verify:visual     # 9/9，其中 A7 是版式一致性
```

`Game.__panels()` 遍历渲染树，把每块面板的标题换算成「相对自己卡片左上角的偏移」：

- 偏移用**逐级累加本地 x/y** 得到，不用 `getGlobalPosition()` —— 后者会被
  `root.scale`（按 dpr 算出来的系数）乘一遍，同一个偏移在不同设备像素比下
  量出来是 23 / 46 / 69，断言没法写成一个确定的数。
- 「相对卡片」这个量在树里推不出来（这些面板的 children 用的是**绝对设计坐标**），
  所以面板把传给 `panel()` 的那组数回填到 `UI.tag.rect`；量出来的仍是真实坐标。
- 断言在 Node 侧独立写死 `dx=23`、`dy` 按字号 12 / 14 —— 改了令牌没同步就是一条红。
- 状态卡（StatusBar）**刻意不在这一组**：它左侧是 40×40 的楼层徽章，徽章就占着短条的位置，
  标题按徽章实际宽度往后量（`STATUS_TEXT_W`），与「短条 + 标题」不是同一种结构。

### 14.4 顺手删掉的东西

| 删掉了 | 为什么 |
|---|---|
| 底部消息条 `LogStrip` 整条 | 玩家不会去读滚动的日志；瞬时反馈（拾取 / 战斗 / 开门）改由棋盘与详情卡自己表达。**`state.log` 保留** —— 它是引擎台账，校验器与 `__probe().lastLog` 仍在读 |
| `card()` 兼容入口 | 它固定不画短条。剩最后一个调用方也没了之后，留着就是坑：谁顺手拿它写新面板，新面板就会缺掉那根短条 |
| 工具栏右侧提示、道具栏空提示、状态栏「已到过 N 层」这类说明文字 | 同一条信息在详情卡里已经有了，重复出现只是噪音 |

## 15. NPC：从「一句话 + 一个模板」到对话与职能造型

反馈里另外两条是「NPC 对话只会显示同一句」与「NPC 模板太差，不同功能的 NPC 样子应该不一样」。

### 15.1 台词轮换（数据 → 引擎 → 面板，一条链）

| 层 | 文件 | 职责 |
|---|---|---|
| 数据 | `data/npcs.json` | 每个 NPC 三段：`talkByFloor`（本层专说）、`greet`（首次见面）、`repeat[]`（之后轮流） |
| 规则 | `src/game/dialogue.ts` | `npcLine(state, data, id, floor)` 按优先级拼池，用 `state.talked[id]` 取模选句 |
| 状态 | `src/game/state.ts` | `talked: Record<string, number>` —— 只记次数，不入档位/背包 |
| 引擎 | `src/game/engine.ts` | 撞 NPC 返回 `StepResult.npc`（`NpcTalk`），**不再由引擎直接开面板** |
| 面板 | `src/render/dialogue-panel.ts` | 底部弹出卡片：名字 + 职能章 + 台词 + 功能引导 + 「交易」/「结束对话」 |

关键取舍：**先说话，再交易**。上一版撞到商人直接弹交易面板，玩家还没读完台词，
交易界面已经盖在脸上 —— 于是「对话」这件事根本没发生。现在顺序倒过来，
由玩家自己按「交易」开摊（原版魔塔就是这个顺序）。

旧字段 `talk`（单句）已删除：同一个 NPC 无论第几次搭话都只说一句，
玩家一撞就发现「对话是假的」。

### 15.2 职能造型：六个剪影，六个「你是干什么的」

`tools/build-assets.py` 的 `NPC_ART` 里，六个职能各有一组造型参数，
用 `_put()` 一个原语画 16×26 像素画（硬边像素块，不是矢量缩放）：

| 职能 | 剪影记号 | 手持物 |
|---|---|---|
| `sage` 指引 | 灰白长袍 + 尖顶软帽 + 白须 | 比人高一截的法杖（顶端宝石） |
| `merchant` 交易 | 暖褐短袍 + **宽檐帽** | 腰侧钱袋 |
| `shop` 属性 | 深绿外袍 + **皮围裙** | 手边一摞金币 |
| `thief` 情报 | 兜帽 + 蒙面（只留眼缝） | 腰侧短匕 |
| `fairy` 祝福 | 青白长裙 + 背后**薄翅** | 星杖 |
| `princess` 主线 | 粉裙 + 长发 + **金冠** | —— |

为什么自己画：第三方免费素材包里**只有一个 NPC 角色**（`NPC_test.png`），
六个职能共用一张图 = 「不同功能的 NPC 长一样」，这正是被反馈的问题。
素材库里也没有第二套可用的多角色 NPC 集。

配色与 `theme.ts` 的 `NPC_ROLE` 一一对应（sage 蓝 / merchant 金 / shop 绿 /
thief 灰 / fairy 青 / princess 粉），**同一职能在整座塔里颜色恒定**：
棋盘上的名牌底、脚下名牌、对话框的职能章、交易面板的职能章，四处同色同字。

回归保护：`verify_npc_art()` 在构建期断言「六个剪影互不相同」「脚踩到最底行」
（底部锚定的精灵一旦浮空，人看起来是在飘）「idle 帧数恰好为 1」。
**呼吸不在素材里** —— 每个 NPC 只有 1 帧静止图，上下浮动由渲染层做刚体位移
（`board.ts` 的 `NPC_BOB_PX` = 1px、`NPC_BOB_MS` = 4200ms）。

> ⚠️ 数据缺口：`thief` / `fairy` 这两个职能**在参考源的地图里从未被放置**
> （role 层里只有 32/33/36/39）。造型、职能色、台词都已就绪，但游戏里见不到 ——

## 16. 场景背景（塔的位面）、塔壁同源与版式重排

本轮反馈原话：

> 把主界面和游戏界面 UI 风格统一，主界面改为上部为星空，下部为绝地，代表塔的位面，
> 更有代入感，地图周边的墙优化和地图的风格一致，各模块间隙加大，不要挤占游戏地图的空间。

拆成五件事，其中三件有反直觉的结论，逐条记在下文。

### 16.1 「主界面」= 场景背景层，不是新做一个开始画面

本项目**只有一屏游戏画面**，没有标题/开始界面。所以「主界面」在这里指的是
**棋盘与面板背后那层场景背景**（用户随后在选型里确认了这一点）。
本轮新增 `src/render/backdrop.ts`，作为 `root` 的**第一个子节点**铺满整块画布。

### 16.2 位面：五锚点 + 按锚点中心线性插值

`theme.ts` 新增 `REALMS`（5 个锚点）与 `realmOf(floor)`（纯函数，楼层夹紧在 1..50）：

| 位面 | 楼层 | 天色（天顶） | 地平线 | 星密度 | 卡片底 / 描边 |
|---|---|---|---|---|---|
| 地底 `depth` | 1–10 | `#090e20` | **0.62** | 0.30 | `#fdf9f3` / `#e4d6c4` |
| 石堡 `bastion` | 11–20 | `#0a1230` | 0.50 | 0.48 | `#fbf9f6` / `#dfd7d0` |
| 高塔 `spire` | 21–30 | `#0a1440` | 0.38 | 0.66 | `#f9f9fd` / `#d9dced` |
| 云廊 `skyhall` | 31–40 | `#0b1850` | 0.26 | 0.84 | `#f8faff` / `#d5dcf5` |
| 星界 `astral` | 41–50 | `#070d3c` | **0.16** | 1.00 | `#f7f9ff` / `#d2daf7` |

**按「锚点中心」（5.5 / 15.5 / 25.5 / 35.5 / 45.5）插值，不按边界插值** ——
按边界插值会在 10→11、20→21 这些档位边界上跳变，按中心插值则 50 层每层都不同且跨档连续。
`horizon`（地平线占画布高度比例）从 0.62 走到 0.16：**越小 = 星空越大**，
第 26 层正好一半天一半地，这个「刚过中场」的手感是定参数的依据。

**星点用确定性 PRNG（`mulberry32`，种子由位面星密度决定），不能用 `Math.random`。**
用真随机的话同一层每次重绘星点都在跳，换层回来一眼就能看出「星星换了位置」，
而且截图基线没法比对。A10 就断言这一点：「第 1 层读一次 → 切到第 2 层 → 切回第 1 层再读」，
两次必须逐位相同。

`Backdrop` 的绘制顺序：天空竖直渐变条带（64 条，每条 ≈4px，看不出分界）
→ 星点（含银河带 + 星云柔光）→ 地平线辉光 → 绝地渐变（30 条）+ 3 层岩脊剪影。
全部 `Graphics`，不引入任何素材；`eventMode = 'none'`（它在最底层，任何点击都该落到棋盘或面板上），
`setFloor()` 里先比 `floorShown`，**同层不重绘**。

> ⚠️ 一个必须写下来的副作用：背景**只在缝里露出来** —— 面板之间 28px、
> 左右边距 20px。所以 `horizon` 的取值区间（0.16 ~ 0.62）是**刻意挑过**的，
> 让它尽量落在棋盘那一屏（约 0.15 ~ 0.59）里；否则低层的岩层整块被下方详情卡/
> 道具栏遮住，玩家根本看不到「绝地」。**调间隙和调 horizon 范围是同一件事的两面。**

### 16.3 塔壁与地图内墙**同源**，而不是调色对齐

先算色差：旧外檐是冷灰蓝 `#8b98ac`，而地图内墙是暖褐 `#433836` / 亮部 `#775c55` ——
**冷暖两套色系**，怎么调都是「后期贴上去的」。

所以 `board.ts` 的 `buildParapet()` 改成**直接平铺地图内墙那张贴图**
（`atlas.terrain('1')` 的 `source.uid` 与地图内墙一致），结构上就不可能不一致：

- 平铺是矩形铺满，塔壁要圆角 → 用 `Container.mask`（Graphics 圆角矩形）裁切；
- **城垛与外缘描边画在 `wall` 容器之外**，否则会被遮罩一起裁平；
- 城垛的凹口**不画**，让星空从缺口透出来（这也是「位面可见」的一处）；
- 保留一组 `STONE` 石材令牌（`face` `#7a5c4e` / `faceLit` `#9a7a68` / `faceDark` `#503c34` /
  `joint` `#2a201c` / `top` `#b08e78` / `inner` `#1f1815` / `edge` `#120d0b`），
  取自那张贴图的实际像素色，给不贴图的地方用（棋盘底板、塔壁内缘阴影）。

**A9 断言钉在结构上，不钉在眼睛上**：

```
parapet source=5 / 地图内墙 source=5      # __wallSources() 比 source.uid，不是比颜色
```

比 `source.uid` 的好处：以后谁把贴图换掉、或又加一层自绘的颜色叠加，只要不同源就立刻红。
颜色可以蒙对，uid 蒙不过去。另留一条像素核对：截图里采塔壁与地图内墙的色，
算色相差（实测 **15°**）并确认 `R > B`（暖色），可写可回归。

### 16.4 间隙加大：靠「吃回黑边」，棋盘一格没缩

这是本轮最值钱的一条。**加高画布不会让棋盘变小**：

```
root.scale = min(w/W, h/H)           // 等比缩放居中
手机竖屏 390×844 比设计稿 420×780 更瘦长 → 缩放系数一直由**宽度**定下（0.93），
上下各有 60~120px 黑边完全没用上。
设计稿加高到 940（比例 2.238，接近手机竖屏 2.16）只是把黑边吃回来：
同一台机器上系数变 0.898，画布铺满 377×844，屏上元素实际尺寸差 < 3%。
**棋盘一格没缩，多出来的全是间隙。**
```

所以「间隙加大」与「不要挤占游戏地图」不矛盾 —— 前提是**画布同时加高**。
只把 `gap` 从 20 调到 28 却不加高，那才真的是在挤棋盘。

`LAYOUT` 重排后的五块面板 + 棋盘（`W:420 H:940`）：

| 模块 | x | y | w | h |
|---|---|---|---|---|
| `hud` 状态卡 | 20 | 28 | 380 | 88 |
| `board` 棋盘**格子区** | 34 | 178 | 352（=32×11） | 352 |
| `toolbar` 操作条 | 20 | 584 | 380 | 32 |
| `detail` 详情卡 | 20 | 644 | 380 | 126 |
| `items` 道具栏 | 20 | 798 | 380 | 114 |

`pad: 20`、`gap: 28`、`boardGap: 40`。**棋盘前后两条缝刻意最宽**：
它们是位面最显眼的两条横带（上面是星空、下面是绝地）。实测间隙：
`top=28 hud=40 board=40 toolbar=28 detail=28 items=28`。

**一条只看源码发现不了的真实缺陷（旧版）**：旧代码拿 `LAYOUT.board`（**格子区**矩形）
当边界去算间隙，而塔壁是**往外画**的（壁厚 14 四边 + 顶部城垛 8）。
于是屏幕上的真实间隙是 `20 − 14 − 8 ≈ −2` —— **城垛压在状态卡上**，
而源码里写的是「间隙 20，很紧凑但没重叠」。修法是给出唯一正确的边界函数：

```ts
/** 棋盘**含塔壁**的视觉矩形。版面计算与断言都必须用它，而不是 LAYOUT.board */
export function boardBox() { … }        // hud.ts
```

**A8 断言**逐个数对照令牌：间隙 28 / 棋盘前后 40、棋盘 `span = 352`（**未缩**）、
棋盘与面板同栏（x 与 w 一致）。

### 16.5 卡片底色随位面，但保持浅色可读

面板配色有两条互斥路线：整体换深色 vs 保持浅色卡片 + 位面色调。**选后者** ——
这一屏有数值、道具名、报价，深色卡片会把可读性拉下来。

做法：`panel()` 的 `fill` 默认值从常量改成 `realm().card`、描边改成 `realm().cardEdge`。
各锚点的 `card` 只在天色偏冷时往冷推一两档、偏暖时往暖推，**亮度基本不动**
（`#fdf9f3` → `#f7f9ff`）。

**性能注意**：`panel()` 是自由函数，浮层在重建时才走一次；但三块**常驻面板**
（`StatusBar` / `DetailPanel` / `ItemBar`）不重建，所以它们各自留一个
`cardGfx = new Graphics()` 与 `repaintCard()`，**只在跨位面锚点时**重画一次 ——
同层重绘纯属浪费。

「当前位面」在 `theme.ts` 里做成**刻意的全局单值**（`setRealm()` 由 `Game.sync` 统一调一次）。
理由：消费它的是没有 `this` 的自由函数 `panel()`，把位面一路穿到每个调用点，
等于把版面函数和游戏状态绑死。本作是单机单场景，任何一刻只有一个位面。
**这个理由写在代码注释里**，否则下一个人会当成坏味道删掉。

### 16.6 加高的画布连带打破了「硬编码视口」的工具

设计稿从 780 改到 940 之后，`tools/shot-web.cjs` 与 `tools/verify-visual.cjs` 里
硬编码的 `viewport: {height: 780}` 会**静默按旧高度裁** —— 画面下半截被切掉而脚本不报错。
改成从渲染层暴露的只读快照读设计尺寸：

```js
const design = await page.evaluate(() => window.mota.game.__layout());   // { W, H, … }
await page.setViewportSize({ width: design.W, height: design.H });
```

同一次 `__layout()` 也把「间隙确实变大了、棋盘确实没缩」一起读出来：

```js
{ gaps: { top: 28, hud: 40, board: 40, toolbar: 28, detail: 28, items: 28 },
  boardSpan: 352,        // == cell * 11，一格没缩
  boardBox: { … }, sameColumn: true }
```

### 16.7 本轮新增的三条断言

`tools/verify-visual.cjs` 从 9 项增到 **12 项**：

|---|---|
| **A8** 版面 | 间隙 28px、棋盘前后 40px，棋盘 352px（未缩）、与面板同栏 |
| **A9** 塔壁同源 | `__wallSources()` 的 `parapet === inner`（同一张素材图） |
| **A10** 位面 | 地平线随楼层**单调**上移（1 层 0.6202 → 50 层 0.16）且**可复现**；背景跟随显示层（浏览第 3 层时 `paintedFloor === 3`） |

## 17. 道具栏按需占位、NPC 比例、怪物按名称重绘

三条反馈：**「移除无用的道具栏，npc 模型改小一点比例适中，怪物模型优化要更符合怪物名称」**。
前两条都藏着一个「原话 ≠ 真需求」的翻译问题，第三条则是素材覆盖不到名字的问题。

### 17.1 「移除无用的道具栏」≠ 删掉功能

先确认了一件事：**道具栏不是无用的**。铁锹 / 地震卷轴 / 炸药 / 上下飞行器 /
楼层传送器 / 圣水 / 金钥匙… 共 12 种**可使用道具**只能从这一栏使用 ——
删掉功能会直接丢掉一条交互路径。

真正的问题在别处：**它空着的时候也占着整整一块版面**。
上一版常驻 18 个空格子、高度写死 114px，于是刚开局就有一块什么都不放的区域。

改成**按件数算高度**：

| 背包里的可用道具 | 高度 | 表现 |
|---|---|---|
| 0 件 | **0px** | 整栏（连底板）不画，`798..912` 这段还给位面背景 |
| 1~9 件 | `34 + 1×36 + 5` = **75px** | 一行槽位 |
| 10 件以上 | `34 + 2×36 + 3 + 5` = **114px** | 两行槽位，卡片底距画布底仍是 28px |

```ts
export function itemBoxHeight(n: number): number {
  if (n <= 0) return 0;
  const rows = Math.ceil(n / SLOT.size);
  return ITEM_HEAD + rows * SLOT.size + (rows - 1) * SLOT.gap + ITEM_PAD_BOTTOM;
}
```

**两个实现上的便宜**（都是位置选得好带来的）：

1. 它本来是**最后一个模块** —— 「自己的高度」不影响「自己的 y」，
   所以高度变成动态的，**没有任何模块需要跟着挪**。
2. 高度为 0 时不只是 `visible = false`，而是从版面的 `placed` 序列里**摘出去** ——
   否则「间隙相等」那条断言会去量一个不存在的方块（见 §17.4 的 A8 调整）。

> 顺带删掉了常驻的 18 格空槽背景。那段代码的存在本身就是上一个设计
> （「常驻占位」）的证据 —— 需求变了，它就该消失，而不是留着「以防万一」。

### 17.2 NPC 比例：用**内容包围盒**量，不用「看着大」

NPC 看着比勇者大。这里有个容易量错的地方：**不能比帧尺寸**，要比
**内容包围盒** —— 帧都是 16×26，画布尺寸一样大，差别全在**内容占了几行**。

量出来的事实：

| | 内容占的行 | 高度 |
|---|---|---|
| 勇者走路帧 | `up` 两帧 `3..25`、`down` 四帧 `4..25` / `5..25` | **21~23** |
| NPC（改前） | `0..25` | **26** → 是勇者的 **1.13 倍** |
| NPC（改后·**静止帧**） | `3..25` | **23** = 勇者的最高帧 → 比值 **1.000** |

修法是把 NPC 的绘制区间整体下移到 `4..25`（再过 `add_outline` 后内容落在 `3..25`），
静止时与勇者**最高**的那一帧同高。

> ⚠️ **这里曾有一个「呼吸帧」带来的 1px 差**，2026-09-23 随呼吸移出素材而消失：
> 那时 `walk` 序列的第 2、4 帧是呼吸帧（上身上移 1px），内容到 `2..25`、高 **24**，
> 比勇者最高的 23 高 1px —— 是个「刻意留着的有界代价」。
> 现在 idle **只有 1 帧**，`walk[i][0]` 就是唯一形态，实数与判据不再有这道缝：
> 见 §18.3 的判据 ⑤。

**断言也跟着改了一次**：第一版 `verify_npc_scale` 拿「某一帧勇者」当基准
（要求 NPC 高度恰好等于 22），结果 6 个 NPC 全红 —— 因为勇者各帧本身就在 21~23
之间波动。改成拿勇者的**极值**当基准后才对：

| 用哪个值 | 结果 |
|---|---|
| 某一帧的高度（22） | 6 个 NPC 假红 |
| 勇者的 **max(高) / min(顶) / max(底)** = `23 / 3 / 25` | 全绿，且判据更严（覆盖所有帧） |

> 教训与 A12 那次一样：**断言红了先怀疑期望值**。
> 拿「一个样本」当基准，在有多帧/多相位的对象上必然假红。

### 17.3 怪物按名称重绘

细节都在 [`assets.md` §13](./assets.md)，这里只记结论：

- 0x72 包的 24 张角色底图**全是人形**，包里没有蝙蝠 / 龙 / 乌贼 / 石头人 / 史莱姆
  —— 所以**换素材解决不了**，只能按名称手绘（与 §15.2 的 NPC 同一套做法）。
- 重绘 **13 只 / 7 种形状**（史莱姆族 4、蝙蝠族 3、石人 / 乌贼 / 龙 / 吸血鬼 / 魔王 2），
  其余 23 只仍取素材。
- 蝙蝠第一版画成了**「锚」**（八行满幅 + 细杆），而**读代码看不出来** ——
  于是把 `bat` / `dragon` 改成**字符模板**画法（形状画在源码里，可读可 diff）。
- 龙的翼 / 尾 / 腿原本共用一个颜色，右侧连成一整团 → 拆成四种色才分得开。

### 17.4 本轮新增的两条断言

`tools/verify-visual.cjs` 从 12 项增到 **14 项**：

| 断言 | 判据 | 抓到过什么 |
|---|---|---|
| **A11** 道具栏 | 空背包 `h=0` 且**不参与排版**（`itemsHidden` 且不在 `placed` 里）；1 件 = 75px；10 件 = 114px 且底距 28px | 期望值在 Node 侧**独立重算**（与 `hud.ts` 的 `itemBoxHeight` 对撞），不是 import 渲染层的函数 |
| **A12** 手绘怪物 | 棋盘上**没有**怪物 `uid === null`（走了程序化兜底）；全部怪物同一个 `source`；落屏帧 ∈ 该怪的 `idle` 四帧且 64×64（raster tile）；6 个取证层里该出现的手绘怪物一只不少（清单**动态**读 MANIFEST，当前 35 只） | 第一次红就是**期望值写错**（按 `idle[0]` 对，而渲染层按相位换帧）—— 见 assets.md §13.8 |

A8（间隙）也跟着动了一处：**最后一个模块的尾隙是自由空间**，不是「两块之间的缝」，
所以它不参与「间隙相等」的比较。空背包时 `detail` 后面本该是 170px 的场景，
第一版拿它当间隙量就会假红。

## 18. NPC 造型再修：先补「头身比」，再修「包里那一版素材」

一句反馈里塞了两件事，性质完全不同：

> **「npc 的模型应该和玩家角色类似，现在的头上长方形太细，身体太宽，新的素材在模拟器中没有生效」**

- 前半句是**造型**问题：§17.2 只把 NPC 的**高度**对齐了，**形状一点没动**。
- 后半句是**链路**问题：跟造型毫无关系 —— 小游戏包里装的还是**上一版图集**。

两件事的共同点是：**都不能靠眼睛判断，都得各欠一条会红的断言。**

### 18.1 「头太细、身太宽」是一句可以量的话

§17.2 那次只量了**高度**（实心行区间），所以「高度一样」被判过了，形状没人管。
这一轮把**宽度**也量了 —— 而且量的不是「最左到最右的跨度」，
是「**含画布中心的那一段**实心像素的宽度」。理由在 18.3。

从 git 里把改前那版素材取出来逐行量（`git show HEAD:assets/atlas/actors.png`），
反馈是**逐字命中**的：

| 智慧老人 `down[0]`，逐行核心宽度 | 改前（HEAD） | 改后 |
|---|---|---|
| 帽子 | 行 3–8 = 12~13 | 行 4–7 = 10~12 |
| **脸** | 行 9–13 = **8** ← 「头上的长方形太细」 | 行 8–13 = **10~13** |
| 肩 | 行 14 = 13 | 行 14 = 13 |
| **躯干 + 下摆** | 行 15–24 = **15** ← 「身体太宽」 | 行 15–19 = 12~14 |
| 下摆收口 | 行 24 = 14 | 行 20–21 = 8~12 |
| 脚 | 行 25 = 8 | 行 22–23 = 8 |
| **实心行** | `3..25`（高 **23**） | `4..23`（高 **20** = 勇者） |
| 最宽行 | **15**，位置在**下摆** | 12~15，位置在**肩** |

形状一句话说清：改前是**上窄下宽的钟形**（8 → 15），
改后是**肩最宽、下摆收口**（10~13 → 12~14 → 8）——后者才是勇者的轮廓。

> ⚠️ 一个容易量歪的地方：改前的「头顶那一块」量出来并不窄（12~13），因为
> **帽子比脸宽**。真正细的是**脸那根 5 行 × 8 列的长方形**。所以判据盯的是
> 「脸所在的行」，不是「整个上半身」。

### 18.2 改后实测（六个 NPC，断言口径）

断言里的口径是：`head = max(核心宽, 行 8..13)`，`hem = max(核心宽, 行 20..21)`，
判据为 **`head ≥ 10`** 且 **`hem ≤ head + 2`**：

| | sage | merchant | shop | thief | fairy | princess |
|---|---|---|---|---|---|---|
| head | 13 | 12 | **10** | 10 | 13 | **10** |
| hem | 8 | 12 | 8 | 12 | 8 | 8 |
| hem − head | −5 | 0 | −2 | +2 | −5 | −2 |
| 最宽行 | 14 | 14 | 14 | 14 | 15 | 12 |

同一口径下改前是 `head 8~16 / hem 14~15`，`hem − head` 最大到 **+7**（商店）。

### 18.3 修法：把行号和列号都收进表，然后记住描边会吃 1~2 列

**① 行号进表。** `NPC_HAT_TOP/NPC_FACE_TOP/NPC_EYE_TOP/NPC_TORSO_TOP/NPC_ROBE_TOP/NPC_FOOT_ROW`
六个常量定死纵向解剖，`_npc_base` 里**不写裸数字** ——
否则下次「NPC 又变大了」会是六个角色各错一点，很难查。

**② 列号也进表。** `NPC_FACE_X/W = 4,8`、`NPC_TORSO_X/W = 5,6`、
`NPC_ARM_X/W = 3,2`、`NPC_ROBE_X/W = 5,6`。原则两条：
**头不比身体窄**，**肩要比下摆宽**。

**③ `add_outline` 是 1px 八邻域膨胀 —— 相邻两段的「绘制」宽度至少要差 2。**
第一版重画就栽在这：头和肩都画 10 宽，结果整只精灵在 12 宽上从头顶平到脚，
**变成一根柱子** —— 单看某一行的数字都对，看整体才不对。
差 1 会被描边抹平，所以下摆从 12 收到 6（可见 8）才算「收腰」。

**④ 为什么宽度要取「含中心那一段」而不是「最左到最右」。**
手持物（法杖 / 钱袋 / 金币 / 短匕）画在身体右侧，描边之后会和身体轮廓连成一片，
跨度就会把道具算进「身体有多宽」里 —— 而「身体太宽」恰恰是这条断言要抓的东西，
**量法不能自己把它放大**。取含中心的那一段正好把独立的道具段排除在外。

**⑤ idle 帧数必须恰好为 1。** 这条是 2026-09-23 把呼吸移出素材之后补上的，
它替掉了原来的「呼吸帧只抬上身」。

> **为什么要留一条断言，而不是删掉 `_breathe()` 就完事**：
> 删代码只说明「现在没画」，挡不住下一个人再加一帧回来 ——
> 而「素材里做上下错位」正是玩家反馈的「抖动时出现压缩」的病根。
>
> 曾经的错误做法（`_breathe()` 把上半身整体抬 1px、再把下摆第一行平移填缝）
> 修过两次、逼近过一次「能用」：先是用平铺的袍色填腰上的横缝，把角色
> **撕成上下两半**（用户原话「抖动时上下分离」），后来改成把下摆首行原样上移。
> 但那条缝**永远**存在，因为「上半身相对下半身位移」必然要求接缝处有补偿，
> 而三种补偿全都在改动像素的形状：
>   · 复制一行填缝 → 腰上多一行（读作「被压了一下」）
>   · 留空不填     → 躯干与下摆之间透背景（「上下分离」）
>   · 整图上移     → 底部锚定，脚离地（「在飘」）
>
> 正解是**分层**：素材只出静止帧，位移交给渲染层做**刚体位移** ——
> 整只精灵上抬 1px，任何像素的相对关系都不变，「压缩」在原理上不可能发生。
> 渲染侧由 A20 从另一头夹住（贴图 / 帧高全程不变、只位移 1px）。

### 18.4 「新素材不生效」= 包内图集是**副本**

- **症状**：IDE 里一切正常 —— 无报错、`atlas.ready = true`、棋盘完整，
  **只是画的是上一版画**。不看对比图根本发现不了。
- **根因**：`dist-minigame/assets/*.png` 是 `npm run build:minigame` 时由
  `tools/copy-minigame-assets.mjs` **拷过去的一份副本**。
  只跑 `npm run assets`（重建图集）或只跑 `npm run build`（网页版）
  **都不会刷新它** —— 包内还是上一版美术。
- **实测证据**：`dist-minigame/assets` 时间戳 `00:31`，`assets/atlas` 是 `01:25`；
  SHA-256 也不同（`actors.png 源=c3e574dc83fb 包=c21d72d2a698`）。
- **修法**：重跑一次 `npm run build:minigame`（现在包内 4 张图集与源**逐字节一致**）。
- **断言**：`tools/verify-minigame.cjs` 新增一条，逐张比 SHA-256 前 12 位。
  **先拿它证明了红**再修的 —— 不写断言的话，这条链路永远靠人记。
  判据用**内容哈希而不是时间戳**：时间戳会被 checkout / 复制 / 打包抹掉，
  而「字节一致」才是「模拟器里看到的就是我刚画的那份」的准确表述。

> 这一步也是本轮唯一**必须重跑构建**的原因：`verify:minigame` 绿的
> 「图集加载成功」只证明**加载成功了**，证明不了**加载的是哪一版**。
> 两条断言管的是两件事，缺一条就会漏。

### 18.5 顺带发现的潜在缺陷（**没修**，记在这里）

`Image.paste(im, pos, im)` 在本流水线里会把 alpha **平方**（实测 102 → 41）。
`bottom_center()` 和图集装配各来一次，于是勇者脚底那层影子被平方两次：
102 → 41 → **7** —— 等于画了个看不见的影子。正确写法是 `alpha_composite`
（对空画布就是逐像素拷贝，实测 102 → 102）。

**这一轮刻意不动它**：修好之后勇者会长出影子，而 NPC 还没有影子，
两只站一起会不协调；要一起补就得先定 NPC 的影子画法。所以先把结论
写成注释钉在 `SOLID_ALPHA` 上面，等补影子的那一轮一起做。

> 它同时也是 §17.2 那次「NPC 假红」的根因：用「非透明包围盒」量勇者时，
> 那两行 alpha=7 的极淡残影被算了进去，量出 22~23。
> 现在所有比例判据一律走实心阈值（`SOLID_ALPHA = 250`，描边是 255、
> 半透明影子 ≤178），**既不受它影响，将来修好了也不会变**。

## 19. 一次四条反馈：两条是真 bug、一条是排版、一条是素材

这一轮的输入是四句话，看着像四个「小毛病」，其实分成四类**完全不同的**问题：

> **「点击楼层浏览返回后角色没了无法继续操作；攻击怪物时角色会变小，改为攻击动画；
> npc对话的内容不会换行；上楼和下楼的素材换成不一样的」**

| # | 反馈 | 真实性质 | 抓它的手段 |
|---|---|---|---|
| ① | 楼层浏览返回后角色没了、无法操作 | **状态机有死路**（最严重：玩家卡死） | A13（行为断言） |
| ② | 攻击时角色变小 | 观感问题，但**有可量的代理量** | A14（量精灵矩形） |
| ③ | 对话内容不会换行 | 版面常量写错（硬编码 32） | A15（量每行像素宽） |
| ④ | 上下楼梯素材一样 | 素材**结构**问题 | A16（量横剖面走向） |

四条的共同点还是那句老话：**都不能靠眼睛判断，都得各欠一条会红的断言。**
`verify-visual` 从 14 项增到 **18 项**（新增 A13–A16）。

### 19.1 楼层浏览：不是"返回没生效"，是**根本没有出口**

先说结论：旧代码的问题不在"返回"这个动作上，而是**选完楼层那一刻就把唯一的出口删掉了**。

```ts
// 旧:  onFloorPicked 的浏览分支
this.browseFloor = f;
this.board.setHeroVisible(false);
this.floorPanel.close();          // ← 出口跟着面板一起消失
this.toolbar.setBrowsing(true, this.state.floor);
```

`browseFloor !== null` 是**全局输入闸门** —— `onBoardClick` / `onKey` / `doStep` 全都
第一行就 `return`。于是选完一层之后：

| 现象 | 原因 |
|---|---|
| 勇者没了 | `setHeroVisible(false)`（浏览别的层，勇者当然不在那一层） |
| 点棋盘没反应 | 输入被 `browseFloor !== null` 整体挡下 |
| 面板上的「关闭」也没了 | 上面那句 `floorPanel.close()` |

触摸设备没有 Esc，**剩下零个出口**。探针实测原话是「点棋盘 0 → 0（点了没反应）」
——这种"静默失效"最容易在自测里滑过去，因为没有报错、画面也正常。

修法的关键是**把出口挪到"面板收起来也还在"的地方**，而不是"别收面板"：

```ts
this.browseFloor = f;
this.board.setHeroVisible(false);
this.board.setFloor(this.state, this.data, f);
this.toolbar.setBrowsing(true, this.state.floor);  // 中间那颗变成「返回第 1 层」并高亮
this.floorPanel.close();                            // 收面板，看得到棋盘了
```

**为什么必须收面板**——这一条是量化之后才定的，不是审美：

| 元素 | y 区间 |
|---|---|
| 棋盘 | `178 .. 544` |
| 楼层面板卡片（`FLOOR_CARD`） | `240 .. 700` |
| 工具栏 | `584 .. 616` |

面板卡片把**棋盘和工具栏一起盖住**。留着面板会有两个后果：
① 玩家看不清自己点开的那一层，"浏览"等于只看一眼角落；
② 面板的遮罩是**全屏**的，把工具栏那颗「返回第 N 层」也盖住 —— 文案换好了却**按不着**。

> 第 ② 条是靠 `hitTest` 抓出来的。当时的现象是"点面板里的楼层格子毫无反应"，
> 用 `page.evaluate` 调 Pixi 的 `events.rootBoundary.hitTest(x, y)` 才发现命中的
> 是 `root.children[10].children[0]` —— 舞台最顶层的**死亡遮罩**（见 19.2 的附注）。
> 面板遮罩同理：`dim` 覆盖全屏且 `eventMode='static'`，所以它下面的东西一律点不到。

**顺带修掉的一个真 bug**：`Toolbar.browseLabel` 一度写成

```ts
get browseLabel() { return this.browsePill.label; }   // ← 读的是 Pixi 的渲染树标记
```

`Pill extends Container`，而 `Container.label` 是 Pixi 用来给节点打标记的字符串
（`'pill'` 之类），**不是按钮上画出来的那串字**。于是断言永远看到标记而不是文案
——等于没有断言。正确写法是 `browsePill.labelText`（`Pill` 自己的 getter）。
这条能活到现在，正是因为在此之前**没有任何断言读它**。

### 19.2 A13：断言「出口一直在」，而不是断言「代码里调了 returnFromBrowse」

A13 全程走真实交互（真点击、真状态），只认四件事：

1. 点「楼层浏览」→ 面板开；
2. 点「第 7 层」→ 面板**收起**、棋盘换成第 7 层、勇者被隐藏、浏览态成立；
3. 工具栏**摆出**「返回第 1 层」（比的是完整文案，不是"非空"）；
4. 点它 → 回到第 1 层、**勇者回到棋盘上**、**棋盘真的能走**（步数 `0 → 1`）。

第 4 条里的"勇者可不可见"是直接量 `board.heroLayer.visible` 的 ——
"返回后角色没了"是用户的原话，直接量它比任何间接推断都贴题。

**搭这条断言时踩了三个坑，都写进注释了**（否则下一个人会重新踩一遍）：

| 坑 | 症状 | 真相 |
|---|---|---|
| `page.mouse.click()` | 点面板里的格子毫无反应，点工具栏却是好的 | Pixi 的命中目标是在**帧**里更新的，move/down/up 挤在同一毫秒时 `down` 会沿用上一次移动的旧目标。改成 move → 停 60ms → down → 停 60ms → up 就正常 |
| 前面几条断言把勇者留在了**阵亡**状态 | 点击全都没反应，看着像"面板坏了" | `A1~A12` 会 `__goto` 跑遍全塔，某些层的落点正在**巫师领域**里 → `showDeath()` 往 `deathLayer` 铺了一张满屏 `hitArea` 的遮罩，它吃掉所有点击。修法是先按 `r` 走游戏自己的重开路径 |
| 期望文案写成「返回第 7 层」 | 一直假红 | 文案报的是**要回到哪一层**（勇者自己那层 = 1），不是正在看的那一层 |

### 19.3 攻击动画：把"变小"翻译成一个可以量的量

「攻击时角色会变小」是观感，但它的成因是可以量出来的。把改前那版挥剑帧逐行 dump：

| 帧 | 身体实心行区间 | 内容最低点 | bottom_center 锚定的后果 |
|---|---|---|---|
| `walk[2]` | `4..23`（**20** 行） | 脚 | 正常站在格底 |
| `attack[2]/[3]` | `2..18`（**17** 行） | **剑尖**（第 25 行） | 身体 85% + **脚离地 7 行 ×2 = 14px** |

两个原因叠在一起：① 弓身突刺那一瞬的身体本来就只有 17 行；② 精灵是**底部锚定**的，
而 attack 帧的最低点是剑尖不是脚，于是整个人被"顶"起来 14px。视觉上就是"变小 + 浮空"。

**修法**：攻击帧整组不用了，精灵全程锁在走路帧；反馈改由 `drawAttackFx()` 的
**时间轴特效**表达（`heroAttackMs` 单变量驱动，全是 t 的确定函数 —— 没有随机数，
所以同一时刻截图必然一致）：

| 层 | 做什么 |
|---|---|
| `heroLunge`（夹在 `heroNode` 与精灵之间） | 沿朝向**平移**：`−1.5 → +4 → 0`（蓄力后拉 → 刺出 → 收招）。平移不是缩放 —— 缩放就是"变小" |
| `attackFx`（画在精灵**之上**，不在 lunge 层里） | 以目标格为圆心的**实心扇形环**刀光 + 近白刃口 + 刃尖亮点；`0.18→0.52` 扫开、`0.52→0.82` 淡出 |
| 命中火星 | `t≈0.48~0.86` 在目标格炸开四道短线 |

两个实现细节值得记：

- **刀光用实心扇形环，不用描边线**。第一版用 `stroke` 画弧，在暖砂石地砖上得到的是
  一条又细又同色系的"U"，几乎看不见。`g.arc(外) → g.arc(内, 反向) → closePath → fill`
  才有**面积**，才压得住底。
- **弧心抬 4px，不是 6px**。抬 6 时弧底会溢出到下一格、压在那格地形上，看着像画错了地方。

A14 的判据全是"可量的代理量"，四个方向各跑一遍：

| 量什么 | 判据 |
|---|---|
| `__hero().size` | 全程**只有一个取值**，且等于待机时的取值 |
| `__hero().frame` | 同上（贴图矩形也不许变） |
| `__hero().fxBounds` | 峰值面积 > 0（渲染树算出来的包围盒，不是"我记得我画了"） |
| `lunge` | 峰值 > 1px |
| 收尾 | 结束后 `attacking === false` 且 `fxBounds` 面积回到 0 |
| 朝向 | 朝 `right` 挥就必须真的转向 `right` |

> `fxBounds` 用的是 `getBounds()` 的**实测**结果，而不是一个自己维护的
> "我画到第几步了"字段 —— 后者只能证明代码跑到了那一行，证明不了真的有东西落屏。

### 19.4 对话折行：`LINE_UNITS = 32` 是一个凭感觉写下的数

`wrap()` 的单位口径是「1 单位 ≈ 1 个字号宽」（中文 1、西文 0.55）。
对话框正文可用宽度 = `CARD.w − 2×UI.pad = 380 − 28 = 352px`，正文字号 11.5px
→ 一行最多 **30** 个单位。而代码里写的是 **32**：

| | 值 |
|---|---|
| `LINE_UNITS`（硬编码） | **32** |
| 32 单位实际排到 | **368px** |
| 可用宽度 | 352px |
| 超出的行数（实测） | **42 / 98 行** |

也就是说"不换行"不是风格问题，是**每一行都捅出卡片右边缘 16px**。

修法是把常量换成**几何算出来的**：

```ts
const BODY_PX   = CARD.w - UI.pad * 2;
const LINE_UNITS = unitsPerLine(BODY_PX, UI.fs.body);   // = 30
```

`unitsPerLine(px, fontSize) = floor(px / fontSize)` 放进 `hud.ts`，
和 `clip` / `wrap` 共用同一套单位。**为什么不只是把 32 改成 30**：
字号、内边距、卡片宽任意一个改动都会让手写的数再次失效，而"算出来"不会。
`trade.ts` 里同样硬编码的 `34`（备注行 `clip(note, 34)`、建议行 `wrap(advice, 34)`）
一并换成 `NOTE_UNITS` / `ADVICE_UNITS` —— 它们同样超宽（391px / 357px vs 352px）。

**顺手补上的中文禁则**。原来的 `wrap` 是纯贪心的，断行点正好落在标点前时会得到
一整行以「，」开头的句子。现在 `wrap` 带两种禁则：

| 禁则 | 处理 |
|---|---|
| 行首不能是收尾标点（`，。、！？：；）」』】》…`） | 把本行**最后一个字挪到下一行**，让标点跟着它 |
| 行尾不能是开启标点（`（「『【《〈`） | 同上（把开引号挪到下一行） |

选择"挪字"而不是"让标点溢出一格"：溢出会捅破卡片，挪字只让上一行少一个字 ——
前者是 bug，后者只是呼吸感。本行只剩一个字时不挪（挪了就是空行）。

A15 从渲染树反推可用宽度（`正文 Text 的 x − 卡片 x = UI.pad`），不在这里抄一份 `14`：
抄一份就多一个漂移点。判据：**46 个 NPC / 105 行全部 ≤ 352px（最宽 345px）、
没有一行以收尾标点开头、没有一行以开引号结尾**。

> 顺带核实了一件事：行变窄会让行数变多，会不会撞上 `MAX_LINES = 7` 的截断？
> 实测最长的 NPC 脚本是 **4 行**（第 12 层的商店），离 7 行还有余量，不用动。

### 19.5 上下楼梯：改的是**结构**，不是明暗

`0x72` 包里只有一张 `floor_ladder`，所以旧版是「下楼梯原样用 + 上楼梯垂直翻转」。
问题在于 `floor_ladder` 本身**近乎上下对称** —— 翻转之后肉眼分不出来，
玩家站在塔里分不清哪一格是往上走。

这一版两张都**手绘**，而且刻意让**结构**不同：

| | 形体 | 怎么读出来 |
|---|---|---|
| 下楼梯 `v` | **侧视下沉阶梯** | 四级台阶自左上沉到右下，越往下越暗、井底近黑 —— 视线"沉下去"（第九轮由「同心方井」改为此画法，见 §21） |
| 上楼梯 `^` | **侧视梯段** | 四级台阶自左下升到右上，每级是一根实心立柱（1px 踏面 + 到底的立面），逐级变亮，右上角 4×4 出口亮光 —— 视线"升上去" |

**为什么必须换结构而不是换明暗**：明暗相反在缩到 32px 之后**等价于翻转**，
玩家学到的只是"亮的是上"这种脆弱的相对线索，换个背景就不成立。

> 后来的修正（第九轮）：上一版把「结构不同」理解成了「两种不同形体」——
> 下＝井、上＝梯。用户反馈那一圈方形**读不出楼梯**，而且跟侧视的上楼梯
> **不像一套**。所以改成**同一族画法的两个方向**：都画成侧视梯段，
> 但一个往右上走、一个往右下沉，明暗逻辑也相反。见 §21。

断言不用"看着像不像"，而是量**横剖面（每列平均亮度）的走向**：

| | 横剖面 | 判据 |
|---|---|---|
| 下楼梯 | `0.70 → 0.40 → 0.62` | 两端明显亮于中间（谷）→ 差 ≥ 0.12 |
| 上楼梯 | `0.211 → 0.643` | 自左向右**单调**变亮、总落差 ≥ 0.15、没有回退 |

再加上两条同一性判据：`up ≠ down`、**`up ≠ flip(down)`**。
第二条正是旧写法会挂的地方 —— 原来的断言只判"逐像素相同"，
"下=floor_ladder、上=垂直翻转"轻松通过，等于没管。

> 断言第一版还因为 `_lum()` 返回的是 **0~255** 而我自己按 0~1 写了阈值，
> 于是拿 `1.25/255` 的微小回退报了红。把返回值归一化之后就对了。
> 这次假红反而有价值：它逼我把"回退"的来源找出来 —— 是踏面左端那 1px 的额外高光，
> 去掉它，`单调变亮` 这条结构特征才干净。

A16 在 `verify-visual` 里**直接读发布出去的那张图集**：把 `dist/assets/terrain-*.png`
交给浏览器 `createImageBitmap` 解码，按 MANIFEST 的帧矩形切出两格再量横剖面。
查的是真正落屏的像素，而不是构建脚本里的意图。另有一条 MANIFEST 文案断言
（`src` 里不许再出现「翻转」）挡住"改了构建脚本忘了重跑 assets"。

### 19.6 本轮新增的四条断言

## 20. 提高像素点密度：素材网格 ×2、文字光栅化跟随屏幕

用户反馈：

> **「在当前页面基础上优化UI，提高像素点点，让画面更精细」**

### 20.1 先量清楚「粗」从哪来 —— 不是渲染器

设计稿 420×940，棋盘格 `cell = 32`，素材画在 16 网格上、运行时 ×2 放大。
在 390×844、`dpr = 3` 的手机上：

```
1 个素材像素 ≈ 32 设计px × 0.898(root缩放) × 3(dpr) ÷ 16 ≈ 5.4 个设备像素
```

也就是说：**画面的颗粒感来自素材分辨率，不是渲染器**。渲染器已经在按
`resolution = dpr` 满分辨率出图。「更精细」只剩两条路，代价差一个量级：

| 路 | 做法 | 代价 |
|---|---|---|
| ① 放大设计稿 | 格子 32 → 40，五块面板全部重排 | 版面与断言动一片 |
| ② 素材网格翻倍 | 出图从 16 网格升到 32 网格、`drawScale` 减半 | 只动构建脚本，落屏**一个设计像素都不变** |

选 ②，外加一件**白捡的**：文字光栅化分辨率。

### 20.2 超采样：`SS = 2`，出图升到 32 网格

> **注**：本节记录的是**第一次**翻倍（`SS = 2` → 32 网格）。
> 第九轮已升到 **`SS = 4`（64 网格）**，并且把手绘地形改成**直接画在 64 网格**
> （超采样只留给第三方位图）—— 见 §21。

`tools/build-assets.py` 新增 `SS = 2` 与两个出图原语：

- **`scale2x()`** —— AdvMAME Scale2x。每个源像素展开成 2×2，块内取值由
  4 邻域决定（`D==B` 取 D、`B==F` 取 F……）。斜向阶梯被抹成真正的斜边，
  直边原样保留 —— **去锯齿但不插值**。双线性会把整张图糊掉，NEAREST 则什么都不做，
  只有 Scale2x 两者都不占。
- **`supersample()`** —— 统一入口：帧边长 < `rasterTile` 才放大。
  0x72 的门原本就是 32×32，再放大一次会落到 64、又被按格子宽压回 32，白丢一半像素。

出图规则（全部写进 MANIFEST，`meta.supersample = 2`）：

| 素材 | 出图网格 | drawScale | 落屏 |
|---|---|---|---|
| 地形（含楼梯、变体） | 32 | 1 | 32px（不变） |
| 常规怪物 | 32 | 1 | 32px（不变） |
| 勇者 / NPC | 32×52 | 1 | 32×52（不变） |
| 道具 | ×2 | 1 | 与原一致 |
| **「大家伙」** | **16（不动）** | **3** | 48px（不变） |

「大家伙」**刻意不参与超采样**：32 × 1.5 是非整数倍，会出现「有的像素占 2 个
屏幕像素、有的只占 1 个」，体型最大的几只反而最毛躁。

### 20.3 细节真正变多的地方：变体挪到 32 网格上生成

第三方位图只有 16×16 的信息，放大不会凭空多出细节。所以**变体改到超采样之后再生成**：
地面杂质、墙的竖缝都是 1px —— 粒度从 1/16 变 1/32，这才是新多出来的细节。

这一步顺带翻出一个**真 bug**：墙变体原本是「按配方重画一层墙」（每行先铺
高光边/砖身、再点缝），在 16 网格上勉强压在 1/255 以内；换到 32 网格立刻崩 ——
底图经 Scale2x 之后缝色占比和配方算出来的不一样（实测平均色偏 2~3/255、
像素偏离 84~116 个，上限 32）。

**按配方重画 = 拿一个近似去对底图，网格越密差得越明显。**
改成「缝整段平移」（每行颜色多重集逐行相同，平均色差恒为 0）之后，断言量的
是「缝有没有动」，而不是「两种砌法差多少」。

### 20.4 文字光栅化：写死 2 → 跟随屏幕

`hud.ts` 的 `label()` 把 `resolution` **写死成 2**。手机是 `dpr = 3`：
文字按 2× 光栅化，上屏还要再拉 1.5 倍 —— 中文笔画细，这一道拉伸就是
「面板文字发虚」的全部来源，而且它影响的是**每一块面板**。

现在由 `app.ts` 在 init 之后调 `setTextResolution(renderer.resolution)` 写进来，
夹在 [2,3]。

### 20.5 断言：两件事都要钉住，缺一条就是假的

32 网格按 1:1 画、和 16 网格按 2× 画，落屏**一模一样** —— 光看画面分不出，
所以新增两条断言：

- **A17 像素密度**：`rasterTile = baseTile × supersample`；逐条地形帧
  `w = rasterTile` 且 `drawScale = 1`；非大家伙怪物 `frame.w × drawScale = cell`；
  **拿发布出去的图集帧和第三方原始素材比边长**（`floor_1` 16 → 32，不是只信
  构建脚本的自述）；最后量落屏的勇者仍是 32×52 —— 网格翻倍若把落屏一起放大，
  这里立刻变成 64×104。
- **A18 文字分辨率**：主页面（dsf=2）断言 `textResolution = clamp(dpr, 2, 3)`。
  **只在本页断言会恒绿**（写死 2 也能过），所以**另开一个 dsf=3 的页面**再验一遍
  —— 期望值必须是 3，写死 2 的实现当场挂掉。

## 21. 地板手绘 + 下楼同族反向 + 密度再翻倍（SS 4）

用户反馈：

> **「优化地板的UI，优化下楼的样式，类似上楼不要一圈的方形，提高像素点密度」**

三条，其中两条指向同一件事 —— **上一轮「提高密度」的做法有上限**。

### 21.1 上一轮留下的问题：超采样有信息上限

上一轮把素材网格从 16 提到 32（`SS = 2`），画面确实变细了。但那时有个没说破的
前提：**超采样不会创造信息**。第三方位图只有 16×16 = 256 个像素的来源，
摊到 32 网格（1024 像素）只是把同一批像素占的地方变小，轮廓更平滑而已。

这一轮用一个指标把它量出来了 —— **每个 16 网格单元内的独立颜色数**
（1.0 = 单元内纯色 = 摊细出来的；越高 = 单元里真有独立信息）：

| 瓦片 | 来源 | 32 网格（上轮） | 64 网格（本轮） | 结论 |
|---|---|---|---|---|
| **地板** | 本轮改**手绘** | 1.07 | **1.76** | 真细节增加 |
| 墙 | 第三方位图超采样 | 1.15 | 1.18 | **几乎没变** —— 摊细而已 |
| 上 / 下楼梯 | 手绘大色块 | 1.04 / 1.01 | 1.00 / 1.00 | 造型本就是大色块，网格不带来新信息 |

所以「再翻倍一次」只能解决**设备像素层面的颗粒**（每素材像素占的设备像素
2.7 → 1.35），解决不了「看起来没有细节」。后者只有一条路：**手绘**。

### 21.2 地板：手绘错缝石板（`_floor()`）

地板占整屏 70%+ 的面积，是最值得手绘的一张。新画法直接画在**出图网格**（64）上：

- **错缝砌法**：上下两行石板，第一行从中间断一次、第二行断两次 —— 平铺时
  不会连成十字网格（这是旧版「地面像一张网」的主因）。
- 缝宽 2px；每块石板贴缝的那 1px 压**倒角**（上 / 左受光、下 / 右背光），
  石板因此读得出厚度。
- 内部撒极稀疏的碎石与磨痕（各 < 1%）。

两个刻意的选择：

1. **碎石用离散几档色，不用连续噪声。** 变体要靠「多重集守恒」派生，
   颜色集必须封闭（见 §20.3 那条教训的延续）。
2. **变体 = 同一配方换种子，不是从成品图上挪像素。** `_floor(seed)` 里
   **只有杂质那一步吃 seed**，缝与倒角用固定种子 —— 缝一旦跟着变，
   平铺就会连不上。这样颜色多重集天然守恒，`verify_terrain ⑤` 量的就是
   「杂质挪了多少」，而不是「两种画法差多少」。

配色仍压在暖砂石族里，所以「地面 / 墙明度比 ≥ 2.0」这条断言**一个字没改**
就继续生效 —— 它描述的是约束（地面必须远亮于墙），不是某个具体画法。

### 21.3 下楼：不是「另一种形体」，是**同一族的两个方向**

上一轮我把「两个楼梯要能区分」理解成了「要画成两种不同形体」，于是
下＝同心方井、上＝侧视梯段。用户的反馈是：

> 「类似上楼不要一圈的方形」

那圈方形**读不出楼梯**（像个坑 / 漏斗），而且和侧视的上楼梯**不像一套**。

修正后的理解：**区分靠方向，不靠换画法。** 两张现在都是侧视梯段，但：

| | 走向 | 明暗逻辑 | 端点 |
|---|---|---|---|
| 上 `^` | 从左下**升**到右上 | 越往上越亮 | 右上角出口亮光 |
| 下 `v` | 从左上**沉**到右下 | 越往下越暗 | 右下角井底近黑 |

两个方向**同时相反**，才是「一眼读出往哪走」；只改其中一个（比如把同一张图
调暗）不够。构建期判据也就从「下＝两端亮中间暗（谷）」改成
「下＝自左向右单调变暗」—— **判据必须描述当前这一版的形体**，否则它会
继续保护一个已经被换掉的画法。

### 21.4 密度再翻倍：`SS = 4`，并且两套放大目标

`SS 2 → 4`（出图 64 网格、`drawScale 1 → 0.5`），落屏设计像素一点不变
（16 × 2 = 64 × 0.5 = 32）。

这里踩到一个真 bug，值得单列 —— **「放大到多少」对两类素材是两套规则**：

| 类别 | 规则 | 为什么 |
|---|---|---|
| 地形 | 统一放大到 **64 网格**（`terrain_raster`，while 循环） | 地形一律占一格、落屏 = cell |
| 角色 / 怪物 / 道具 | **源 ×SS**（`supersample`，固定次数） | 落屏尺寸各不相同，统一到 64 会把小道具放大一倍 |

门的源本来就 32×32（不是 16 网格那一套）。按「源 ×SS」它会到 **128×128、
落屏 64px —— 一扇门顶两格宽**（上一轮 `SS = 2` 时它恰好卡在 32 被跳过，
所以一直没暴露）。修法是地形改走「放大到目标网格为止」。

「大家伙」这次也一起超采样了（64 网格 × 0.75 = 48px）。它上一轮不参与，
理由是「非整数倍会毛躁」—— 那是**倍数只能取整**时代的约束；现在不跟的话，
它反而是全屏像素最粗的东西（每素材像素 8 个设备像素 vs 别人的 1.35）。

### 21.5 本轮最值钱的三条

1. **判据别依赖会变的中间量。** 「大家伙」的判定原本是 `drawScale > 2`。
   倍数变成小数（0.5 / 0.75）之后，这条**静默变成「0 只大家伙」**，
   于是 A5a 拿「非 BOSS 必须装进一格」去卡 BOSS，红得莫名其妙。
   改成**按落屏尺寸判定**（`frame.w × drawScale > cell`）才算落在语义上。
2. **判据要跟着画法一起改。** 楼梯判据原本保护「下＝井（谷）」。下楼换画法后
   它立刻红 —— 这是好事；但如果不红（比如新画法恰好也是谷形），它就会
   继续保护一个不存在的形体。改判据时要问「它现在保护的是什么」。
3. **「更精细」有两种，别混为一谈。** 设备像素层面的颗粒（超采样能解决）
   和细节层面的密度（只有手绘能解决）。上一轮只做了前者，这一轮补上后者 ——
   21.1 那张表就是两者差距的实测。

## 22. 墙也手绘：错缝砌法 + 手绘压顶（§21.7 待办的兑现）

上一轮的诚实说明：地板手绘了，墙还是第三方 16×16 位图超采样 —— 满屏铺开
时墙比地板粗。这一轮把它补上。

### 22.1 为什么墙非改不可

§21.1 的表格里，墙是「超采样不产生细节」的实锤：32 网格 → 64 网格，
单元内色数 1.15 → 1.18，几乎没动。地板手绘后是 1.76。也就是说棋盘上
**两种大面积地形，一种有细节、一种没有**，并排看落差非常明显。

### 22.2 画法：错缝砌法（`_wall()`）

结构直接写在 64 网格上：

- 一层砌层 16 行（砖身 12 + 横缝 4），竖缝间距 32，**相邻层错开半块（16）**
  —— running bond，砖身恒为 28×12。
- 缝宽 4px（与地板的缝同宽）；贴缝 1px 倒角（上/左受光、下/右背光）。
- 残缺四件套：缺角 2×2、斜向裂纹 5px、锈斑 3×2、麻点单像素，**数量写死、
  颜色离散** —— 变体只换位置，配色多重集守恒（§21.2 同一套做法）。

两个平铺上的硬约束（缩略图上完全看不出来，只有数值得出）：

1. **缝宽与缝距必须整除格子**，且横缝在格子边界处「每张各出半道」——
   否则整片墙每隔 32px 会多出一条变细的缝。用 3×3 平铺逐列数缝色验证过：
   缝宽全部为 4、间距全部为 16，边界处由相邻瓦片补齐。
2. **压顶必须吃掉层间的整道横缝**（`_wall_cap`，投影 4 行正好盖住它）——
   否则压顶底下会留下 2px 孤零零的缝，看着像画歪了一条线。

压顶也一并手绘：第三方 `wall_top_mid` 在 16 网格上只有 4 行内容，超采样后
压在手绘墙身上会明显比墙身粗 —— 「只换了一半素材」的典型症状。

配色仍留在 0x72 的墙色族里（砖身 `(78,63,60)`、缝 `(38,32,31)`），灰缝只是
比原来的 `(34,34,34)` 略偏暖 —— 那个值正好等于史莱姆的深色，怪物会「粘」
在墙上。实测地面/墙平均亮度 **0.631 vs 0.219，比值 2.88**（断言卡 2.0，
一个字没改就继续生效）。

### 22.3 变体路线的回归

墙的变体曾经必须「从成品图上挪像素」（竖缝整段平移），因为第三方位图没有
配方。改手绘之后有了配方，变体就退回和地板同一套「**同一配方、换个种子**」
—— 颜色多重集**天然守恒**，drift 断言量到的就是「残缺挪了多少」。
`_wall_palette()` / `_row_major()` 那套「从底图推色再补位」的代码随之删除。

### 22.4 断言：A19 墙必须是手绘错缝砌法

新加一条运行时判据（`verify-visual.cjs` A19，直接量发布出去的图集帧）：

| # | 判据 | 抓的是什么 |
|---|---|---|
| 1 | 调色板 ≥ 5 色 | 0x72 位图恰好 3 色，超采样不会多出颜色 |
| 2 | 每层砌层都有缝列 | 缝没了 = 砌法没了 |
| 3 | 0/2 层缝列同相、0/1 层错开 | running bond 的定义 |
| 4 | MANIFEST `src` 含「手绘」 | 改了脚本没重跑 assets |

判据绑的是**砌法语义**，不是颜色值 —— 将来调配色不会红，退回位图必红。

顺带：A17 的「比边长」参照物从 `wall_mid` 换成 `wall_goo`（岩浆）——
地板、墙都手绘之后，仍在走超采样的地形只剩岩浆/虚空/门。
**参照物本身也会过期**：素材每手绘一张，就要换一次参照物。

## 23. 怪物脚下的点、呼吸节奏、勇者的三件装备（2026-09-23）

### 23.1 「脚底的点」到底是什么 —— 一次分层定位

玩家原话：「移除怪物脚底的点或者阴影」。这句话**在源码里搜不到任何对应物**：
没有 `shadow`，素材帧底也没有半透明像素（实测 35 只怪的实心像素底部一律是 31，
画布 32 行全满）。所以第一步不是改，而是**先定位它在哪一层**：

1. **隐藏实体层再截图**（`board.children[3].visible = false`）→ 怪物消失了，
   点还在 → 看似排除了「点属于怪物精灵」。
2. 逐个隐藏其余层，点始终在 → 只剩 `terrainLayer`。
3. 但地板贴图的调色板只有 5 种**棕色**，而点会随怪物主色变化
   （绿史莱姆下面是绿的、红史莱姆下面是红的）→ 矛盾，说明第 1 步的结论是错的。
4. 改成**遍历整棵渲染树取包围盒**，筛出落在该格的节点：
   `b/3/0/2`，一个 **6×4** 的 Graphics，全局坐标 `(111,204)` ——
   正好在第 (2,0) 格的下缘中央。

回源码一眼就找到了：`board.ts` 的 `gradeDot`，「怪物脚下的战斗评级指示灯」，
颜色 `shade(怪物主色, -0.62)` —— **所以它才「随怪物变色」**。
它挂在**每只怪自己的 Container** 上（不是实体层直接的孩子），
这正是第 1 步按层隐藏会看错的原因。

> ⚠️ **这一步真正的坑在工具上，不在游戏里。**
> 第 1 步我用 `--after` 传表达式，表达式含空格被 shell 拆成多个参数，
> `--after` 只收到 `(()=>{const` —— **隐藏根本没执行**。
> 而我看到的新截图与旧截图**字节数完全相同**，却先入为主读成了
> 「点还在，所以不在实体层」，白白多绕了两轮。
>
> **判据**：两次不同操作的截图**尺寸/字节完全一致**时，先怀疑操作没生效，
> 再谈结论。这次是靠 `ls -la` 三个文件同为 20059 字节才发现的。

### 23.2 移除之后：怪物回到格底

点存在的原因是 `standY = S - plateH - 1 = 22` —— 精灵被抬高 10px 给它腾地方。
点没了，抬高的理由也没了，于是 `standY` 改回 `S`：**脚踩格子下沿**。
这既填满了格子，也让待机呼吸的「抬起 1px」有了「脚离地」的读法
（原来脚下本来就悬空 10px，抬 1px 只是在一段空白里动，看不出呼吸）。

评级信息没有丢：它在 HUD 的战斗面板里（`hud.ts:621` 用同一份 `GRADE_STYLE`）。
`BoardHooks.gradeFor` 这个只服务于脚下点的回调也随之删掉
（留一个没人读的 hook，下一个人会以为脚下还有点）。

**A5b 反了过来**：改前断言「每只怪恰好一个指示灯、且落在格内」，
现在断言「**脚下干净** —— 精灵之外只留 BOSS 圈」。
`bossRing` 因此也补了 label（生产构建压缩类名，只能按 label 找）。

> ⚠️ 反向断言有一种特有的假绿：`dotCount === 0` 可能只是
> 「`label === 'gradeDot'` 永远找不到东西」（label 被改名、或被构建抹掉）。
> 所以同一条断言里带一个**探针**：数一遍 NPC 脚下的 `npcPlate`，必须 > 0。
> 数不出来就说明「按 label 找子节点」这条路断了 —— 那时报红是对的。
> 实测探针拿到 **46** 个名牌，A5b 报「479 只脚下干净（BOSS 圈 7 个）」。

### 23.3 呼吸：从 1.2s 到 2.6s

改前的周期（怪物 1.2s / NPC 2.4s）实测「能看见，但吵」：1.2s 一个来回
意味着**每 540ms 就有东西跳一下**，而一层楼同时有十几二十只怪、
相位又是错开的 —— 结果是画面上永远有某一处在动。那不是呼吸，是满屏节拍器。

| 项 | 改前 | 改后 | 理由 |
|---|---|---|---|
| 怪物周期 | 1200ms | **2600ms** | 人静息呼吸约 3~4s 一次，棋盘上不该比人快 |
| NPC 周期 | 2400ms | **4200ms** | 站着的人更慢 —— 不该动得像喘气 |
| 占空比 | 45% | **50%** | 1px 方波只有两态，两端停留等长才像呼吸；一头长一头短像打拍子 |

**相位换了算法。** 原来是 `数组下标 × 137 % 周期`，而 `entityViews` 会因换层整体重建 ——
同一个下标在不同楼层对应的是**不同的怪**。下楼再上来，同一格怪的呼吸相位就变了，
玩家看到的是「刚还在喘的怪，一下楼就换了节拍」。
现在用 key 的 FNV 散列 × 0.618：同一格 + 同一只怪相位恒定，
且相邻格子的相位被黄金比拉开（直接取模会让一排怪从左上到右下依次点头，
比同步更出戏）。

> ⚠️ **改周期必须同步 `verify-visual.cjs` 的 `BOB_WINDOW_MS`**：
> A20 的采样窗口要盖住一个完整周期，否则可能只采到「抬起」一档，
> 误报「呼吸没生效」。窗口从 3000 提到 **5600**（NPC 周期 4200 的 1.33 倍）。

### 23.4 勇者的三件装备 + 挥剑帧接线

按玩家要求「增加剑，盾，铠甲」，勇者从 ArMM1998 的切图改成**程序化手绘**
（16×26 网格）。工艺细节与「剑 2 列 / 盾 4 列」的描边算术、
以及那条「判据色必须彼此远离」的新断言，见 `docs/assets.md` §9.2。

渲染侧要记的有两件事：

**① 挥剑帧原本是死素材。** `build_actor_sheet()` 产出走路 + 挥剑两套帧，
但 `refreshHeroTexture()` 只调 `heroFrame('walk', …)` —— 16 帧挥剑素材画完没人用，
而 `verify_hero_art` 还在为它把关，**断言全绿、东西是死的**。
弃用理由写在一条历史注释里：当年 ArMM 的挥剑帧「身体弓成 17 行」「剑尖成了
内容最低点、脚离地 7 行」。**重画后这两条都不成立了**（解剖表在自己手里），
实测四向 `walk[0] (4,23) 20 行` → `attack[0] (4,23) 20` / `[1] (2,23) 22` /
`[2] (0,23) 24`：**底行恒为 23，行数变化全部来自向上伸的剑**。
于是接线：`refreshHeroTexture` 按 `attackFrameIdx()` 在 walk / attack 之间切。

**② 挥剑帧的宽度会横向溢出。** 它的画布原本是 20 列，图集装配里
`bottom_center(fr, 20, 26)` 把这个宽度固定下来 → 图集帧 **80×104**、落屏 **40px**，
比 32px 的格子还宽。抬剑只改 y，横向范围压根没变，那 4 列是白送的。现在两套帧同为 16×26。

**A14 因此改成两条**：

- 正面：挥剑期间 `anim` 必须出现过 `'attack'` —— 只断言「尺寸不变」抓不到
  「没接上」（一个从不换帧的实现同样尺寸恒定，这正是当初漏掉它的原因）；
- 反面：`size` / `frame` 的**尺寸**仍必须全程只有一个取值 —— 两套帧同尺寸，
  所以「不变小」依然成立。这里量的是尺寸而不是帧身份，接帧不会让它红、尺寸变宽才会。

实测输出：`anim=walk/attack`，形体恒为 `32×52`，刀光面积峰值 7136px²。

`npm run verify:all` 四套全绿：

| 套件 | 结果 |
