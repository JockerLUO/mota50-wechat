## 1. 候选源码评估

搜索「魔塔 50 层 源码」后评估了以下候选：

| 仓库 | 语言/形态 | 授权 | 完整度 | 结论 |
|---|---|---|---|---|
| `m8705/MAGIC-TOWER-JS` | jQuery + Canvas | **GPL-3.0** | 51 层完整数据、33 只怪物、地图三层阵列齐全 | ✅ **选为数据来源** |
| `motajs/mota-js` | 现代 JS 引擎框架 | **BSD-3-Clause** | 引擎完整，但**不含原版 50 层具体关卡数据** | ✅ 选为**公式**权威 |
| 其余若干个人复刻 | 混杂 | 无 License | 多数只有前几层，或数值自创 | ❌ 排除 |

### 上游自述：作者承认只写完了前 10 层的事件

`m8705/MAGIC-TOWER-JS` 的 README 原文（**这是判定完整度最有力的证据**，因为出自作者本人）：

> 「这是一个移植到 HTML5 平台的50层魔塔游戏，使用 Canvas 技术开发，
> **游戏还未开发完成，存在一些Bug，但大部分功能都已经实现，只写完了前10层的事件部分。**」

这句话直接印证了 `docs/known-gaps.md` 的核心结论：区域边界通路只有第 10 层有实现
（`event.js` 的 `eventHappened[7]` 分支），并不是我们的误判。

README 还给出了各文件的职责划分，与归档内容逐一对应：

| README 描述 | 实际文件 |
|---|---|
| 「在 **data.js** 内可以修改角色属性和地图数据」 | `js/data.js` |
| 「在 **role.js** 内可以修改怪物对象的信息」 | `js/role.js` |
| 「在 **action.js** 内可以修改对话文本的内容」 | `js/action.js` |
| 「在 **event.js** 内修改事件处理的逻辑」 | `js/event.js` |

另注：「该项目使用的图片来源于网络，非本人所有，仅用作学习用途。」—— 本项目**不使用**其图片资源。

### 归档完整性（本轮修正）

上游 `js/` 目录的真实文件：

```
action.js  8820     data.js   46771    event.js  52464    fight.js   2835
graph.js  23499     loader.js   210    main.js     797    role.js    4727
storage.js  801     lib/（目录）
```

**起初只归档了 5 个文件，遗漏了 `action.js`、`storage.js`、`main.js`、`loader.js`。**
其中 `action.js` 的遗漏影响最大 —— `data/items.json` 的 `usableEffects` **引用了它却没有原始依据**。

补入后逐条核对，**此前的推断全部正确**（见 §2.5），并额外取得了两批高价值信息：
商人分楼层商品清单、智者提示中的机制事实。

> **教训：** 归档第三方仓库时要按**上游的真实文件清单**核对，而不是只取「当前看起来需要的」几个文件。
> 用 `gh api repos/<owner>/<repo>/contents/<dir>` 列目录最省事。
> 归档后可用字节数比对佐证忠实性（本项目的 `mota50-role.js` 与上游 `role.js` 均为 4727 字节 ✓）。
> 另一个廉价的自检手段：**扫描「被调用但未定义」的函数**。
> 本项目正是靠这一步发现缺了 `use` / `buy` / `talk` / `saveData` / `loadData` / `pic` / `replay` 七处实现。

### 选择理由

**为什么不用 `mota-js` 当数据源：** 它是一个**引擎**而非原版关卡的载体 —— 提供的是事件系统、
战斗结算、UI 框架的通用实现，其示例关卡并不是原版 50 层。所以它适合定公式，不适合供地图。

**为什么用 `m8705/MAGIC-TOWER-JS` 当数据源：** 它是目前能找到的、**唯一带完整 51 层数据阵列**的公开实现。
它的三层数据（地形 / 角色 / 道具）结构清晰、可直接解析，且数值与社区基准帖能逐条对上 ——
这一点很关键：**如果它数值对不上基准帖，就不能用。**

**排除无 License 的仓库：** 「没有 License」不等于「可以随便用」，而是「默认保留全部权利」。
相比之下 GPL-3.0 至少明确了条件。虽然 GPL 有传染性（见 ATTRIBUTION §3），但它**是可知的**，
而未知授权连风险评估都做不了。

## 2. 参考源码结构解析

### 2.1 全局状态：`mota50-data.js:var player`

```js
var player = {
    att: 10, def: 10, hp: 1000,          // 初始属性
    coin: 0,                              // 金币
    yellowKey: 0, blueKey: 0, redKey: 0,  // 三色钥匙
    sword: 0,   // 0~5，当前剑等级
    shield: 0,  // 0~5，当前盾等级
    item: [],                             // 持有的道具 id 列表
    floor: 1,
    wentFloor: [1],                       // 到过的楼层（供传送器列表用）
    buyTimes: 1,                          // 商店购买次数，初值 1（见下方注释）
    ...
};
```

**两处关键信息：**

1. **没有 `exp` / `level` 字段** → 原版无经验等级系统（详见 `docs/mota50-numeric-system.md` §2）。
2. `buyTimes: 1` 上带着原作者的注释：
   > 「在商店购买的次数，由于金币计算公式原因（0次和1次购买金额相同），因此此次必须填1」

   这解释了为什么定价公式 `10n(n−1)+20` 的 `n` 从 **1** 起 —— 第 1 次购买就是 20 金币。
   本项目在 `core/shop.mjs` 中强制 `n ≥ 1` 并对非法值抛 `RangeError`。

### 2.2 三层数据阵列

原版把每层地图拆成**三个等长的扁平数组**：

| 层 | 变量 | 内容 | 编码 |
|---|---|---|---|
| 地形 | `floor[n]` | 墙 / 地板 / 楼梯 / 门 / 岩浆 / 星际空间 | 图例编号 0~11 |
| 角色 | `role[n]` | 怪物 / NPC | 怪物 1~31；NPC 32~39 |
| 道具 | `item[n]` | 可拾取物 / 可放置物 | 1~32 |

**寻址约定：`下标 = y × 11 + x`**，`x, y ∈ [0,10]`，`y` 向下增长，每层固定 **121** 格。

> **易错点：** 打印这些阵列时，值 `10`、`11` 会占**两个字符宽度**，
> 让 11 个值的行看起来像 12~13 个字符。核对行宽时不要被误导 ——
> 本项目在 `tools/import-mota50.mjs` 中一律先转成单字符符号再输出，就是为了避开这个坑。

### 2.3 地形图例

来源：`mota50-graph.js` 的绘制分支；通行性来自 `mota50-event.js:function checkFloor`。

| 编号 | 本项目字符 | 名称 | 可通行 | 备注 |
|---|---|---|---|---|
| 0 | `.` | 空地 | ✅ | |
| 1 | `#` | 墙 | ❌ | |
| 2 | `D` | 牢门 | ❌ | 剧情事件开启，**不消耗钥匙**（第 2 层中级卫兵守） |
| 3 | `v` | 下楼梯 | ✅ | 进入 `floorIndex − 1` |
| 4 | `^` | 上楼梯 | ✅ | 进入 `floorIndex + 1` |
| 5 | `~` | 岩浆 | ❌ | 需地震卷轴/铁锹改变地形 |
| 6 | `*` | 星际空间 | ❌ | 第 50 层背景。⚠️ 参考实现的 `checkFloor` **漏判此地形** |
| 7 | `y` | 黄门 | ❌ | 消耗 `yellowKey` |
| 8 | `b` | 蓝门 | ❌ | 消耗 `blueKey` |
| 9 | `r` | 红门 | ❌ | 消耗 `redKey` |
| 10 | `a` | 自动门 | ❌ | 击败指定怪物后自动变空地（第 8 / 30 / 44 层） |
| 11 | `w` | 假墙 | ✅ | 外观同墙，撞一次变空地。**隐藏通路的载体** |

### 2.4 角色编号

来源：`mota50-role.js:getEnermey(num)`。

| 编号 | 类别 |
|---|---|
| 1–31 | 怪物（33 只，编号 8 = 吸血鬼、25 = 魔王、27 = 大法师、29 = 骑士队长、37 = 魔龙、38 = 大乌贼） |
| 32 | 智慧老人 sage |
| 33 | 商人 merchant（**卖钥匙**） |
| 34 | 小偷 thief |
| 35 | 仙子 fairy |
| 36 | 公主 princess（通关目标） |
| 37 | 魔龙 dragon ⚠️ 与怪物编号空间重叠 |
| 38 | 大乌贼 kraken ⚠️ 同上 |
| 39 | 商店 shop（**卖属性**） |

> **注意 37 / 38 的双重身份：** BOSS 怪「魔龙」「大乌贼」在 `role` 层用 37 / 38，
> 与 NPC 编号段重叠。解析时**不能只按编号判断是敌是友**，必须结合 `getEnermey` 的实际分派。
> 这是参考实现的编号设计缺陷，本项目在导入时显式处理并按名称归类。

### 2.5 道具语义的源码复核（`mota50-action.js:use(n)`）

补入 `action.js` 后，对 `data/items.json` 里 12 项 `usable` 道具的语义做了逐条复核。
**复核结果：此前仅凭调用点推断的语义全部正确**，并额外澄清了两处。

| 道具 | id | 源码实现 | 本项目建模 | 结论 |
|---|---|---|---|---|
| 圣水 | 5 | `player.hp *= 2` | `mulStat hp ×2` | ✅ |
| 金钥匙 | 9 | 遍历 121 格，把 `===7`（黄门）改为 0 | `clearTerrain terrain:7 currentFloor` | ✅ |
| 怪物书 | 10 | 切换 `isLookingBook` 面板 | `toggleUi monsterBook` | ✅ |
| 记事本 | 11 | 切换 `isLookingNoteBook` 面板 | `toggleUi notebook` | ✅ |
| 铁锹 | 13 | 挖掉**上下左右四格**中值为 `1`（真墙）的格 | `breakWall adjacent4` | ✅ |
| 雪花 | 14 | 遍历本层，`===5`（岩浆）→ 0 | `clearTerrain terrain:5 currentFloor` | ✅ |
| 地震卷轴 | 15 | 遍历本层，`===1`（真墙）→ 0 | `clearTerrain terrain:1 currentFloor` | ✅ |
| 对称飞行器 | 16 | 传送到 `(12−x, 12−y)`，且该格地形/角色/道具都为空才生效 | `teleportSymmetric` | ✅ |
| 向下飞行器 | 17 | `floor--` | `changeFloor delta:-1` | ✅ |
| 向上飞行器 | 18 | `floor++` | `changeFloor delta:+1` | ✅ |
| 炸药 | 20 | 清除上下左右四格的角色，但 `canUseBomb` 排除 `a>=32`（NPC）与 `a∈{3,8,25,27,29}` | `bomb adjacent4` | ✅ **本轮可精确化** |
| 楼层传送器 | 32 | `prompt` 输入 1~49，且**要求 `wentFloor` 已包含该层** | `openFloorSelect range:[1,49]` | ✅ **并证实「只能去已到过的楼层」** |

**两处澄清：**

1. **炸药的排除名单现在是精确的**：源码 `canUseBomb(a)`：
   ```js
   if(a>=32 || a===3 || a===8 || a===25 || a===27 || a===29) return false;
   ```
   即**不能炸**：所有 NPC/道具（≥32），以及 5 只 BOSS ——
   **骷髅队长(3)、吸血鬼(8)、魔王(25)、大法师(27)、骑士队长(29)**。
   注意 **魔龙(37)、大乌贼(38)、骑士队长(29)** 不在名单里 —— 骑士队长可炸，魔龙和大乌贼因编号 ≥32 而被排除。
   这解释了为什么「44 层的两个高级卫兵(23)可以炸掉，但 BOSS 不行」。
   本项目 `items.json` 的 `bomb` op 描述应据此改为**按 roleId 白名单排除**，而不是笼统的「非 BOSS」。

2. **楼层传送器只能去已到过的楼层** —— 这条对 `docs/known-gaps.md` §1 的判断是决定性的：
   它**不能充当向上出口**，是回溯工具而非推进工具。

## 3. 转换流程

### 3.1 工具

`tools/import-mota50.mjs` —— 把参考源码的三层阵列转成本项目的楼层 JSON。

```bash
# 生成 data/floors/*.json + index.json + monster-placement.json
node tools/import-mota50.mjs

# 只做结构自检，不写文件
node tools/import-mota50.mjs --check
```

### 3.2 处理步骤

| 步骤 | 说明 |
|---|---|
| 1. 解析源码 | 用 `node:vm` 在沙箱中执行 `mota50-data.js`，取出 `floor` / `role` / `item` 三个阵列（**不 `require`，避免污染全局**） |
| 2. 建立查表 | `buildLookup()` 把图例编号 → 字符、角色编号 → 怪物/NPC id 两套映射建起来 |
| 3. 解析每层 | `parseLayer()` 逐格转换：地形拼成 11 行字符画，角色与道具收进 `entities` |
| 4. 楼梯修正 | 采集所有 `3`/`4` 格作为 `stairs`，用 BFS 找目标层的最近可站立格作为落点 |
| 5. 结构自检 | 校验每层 121 格、字符仅出现在图例内、实体不越界、楼梯落点可站立 |
| 6. 特殊标记 | 识别 BOSS 守道具（怪物与道具同格）、墙内隐藏道具（标 `hidden`） |
| 7. 合并楼记 | 把 `data/floor-notes.json` 的机制说明并入对应楼层 |
| 8. 输出 | 51 个 `floor-NN.json` + `index.json` + `monster-placement.json` |

### 3.3 转换中解决的具体问题

| 问题 | 现象 | 处理 |
|---|---|---|
| **楼梯落点入墙** | 第 32 层的下楼梯落点在目标层是墙，玩家会被卡住 | BFS 就近修正到可站立格，并在该楼梯上标注 `arriveAdjusted: true`，保留原始落点便于对照 |
| **墙内道具被误判为错误** | 第 14 层红钥匙、第 41 层下楼器直接放在真墙内 | 识别为**刻意设计的隐藏道具**，标 `hidden: true`，校验器接受该标记而非报错 |
| **BOSS 守道具** | 第 15 层大乌贼与铁锹同格、第 35 层魔龙与雪花同格 | 识别为合法设计（击败后道具仍在原地），标记后不计入重叠错误 |
| **40 / 49 层无上楼梯** | 校验器报「出口缺失」 | 判定为原版设计（靠传送道具），在 `floor-notes.json` 注明 `exit` 方式，校验器对有 `exit` 说明的层放行 |

## 4. 转换结果对照

### 4.1 规模

| 项 | 参考源码 | 本项目 | 一致 |
|---|---|---|---|
| 楼层 | 51（0~50） | 51 | ✅ |
| 每层格子 | 121（11×11） | 121 | ✅ |
| 怪物种类 | 33（真魔王另补） | 34 | ✅ 补 1 |
| 怪物放置点 | 477 + 2 = **479** | 479 | ✅ |
| 道具放置点 | 396 | 396 | ✅ |
| NPC 放置点 | 48 − 2 = **46** | 46 | ✅ |

> **那 `+2 / −2` 是什么：** 魔龙（37）与大乌贼（38）在地图上属**怪物**，但编号落在 NPC 段（≥32）。
> 按编号机械统计会把这 2 个错判成 NPC —— 这正是 §2.4 提到的编号重叠缺陷的实际后果。
> 本项目在导入时按 `getEnermey` 的实际分派归类，因此怪物 479 / NPC 46 才是正确值。

### 4.2 关键楼层抽查

| 层 | 参考源码 | 转换结果 |
|---|---|---|
| 1 | `floor[1]` 含 1 个上楼梯 `4`、7 个黄门 `7`；`item[1]` 在 `(1,10)` 放 32 | `floor-01.json`：up→2、黄门 7 扇、`npc:sage@1,10` ✅ |
| 10 | `floor[10]` 有 `3`(下)、4 个黄门、1 个红门、2 个自动门；`role[10]` 含 3 = 骷髅队长 | `floor-10.json`：BOSS 骷髅队长在场；**无上楼梯**，由剧情事件生成 ✅ |
| 30 | `floor[30]` 有 2 个上楼梯 `4`、1 个自动门 `10`、**无下楼梯** | `floor-30.json`：up→31 ×2，无 down ✅（原版如此，见 `known-gaps.md`） |
| 50 | `floor[50]` 全为 `6`（星际空间），中央 5×5 房间，`role[50](5,5)` = 25 = 魔王 | `floor-50.json`：`*` 地形，`demonKing@5,5`，无任何楼梯 ✅ |

### 4.3 与社区基准帖的数字对照

| 项 | 本项目 | 基准帖 | 差异 | 状态 |
|---|---|---|---|---|
| 黄钥匙（可比四区合计） | 169 | 184 | 少 15 | ⚠️ 已知，见下 |
| 蓝钥匙（可比四区合计） | 20 | 23 | 少 3 | ⚠️ 同上 |
| 门（黄/蓝/红） | 239 / 39 / 11 = **289** | — | — | ✅ 与钥匙总数 193 对比：门多 96 |
| 全塔金币（怪物） | 21842 | 18145 | +20.4% | ⚠️ 统计口径不同 |
| 一区/二区/五区楼层范围 | 1–10 / 11–20 / 41–49 | 同 | 一致 | ✅ |

**钥匙差异的成因（本轮已从「推测」升级为「逐区核对」）：**

基准帖的 `totalKeys` **包含 `merchantKeys`（商人出售的钥匙）**，而参考源码的 `role` 层
把商人放为 NPC（`sourceId 33`），**不携带钥匙实体** —— 商人卖的钥匙是在对话中动态授予的，
不存在于地图数据里。所以本项目统计必然偏少。

补入 `action.js` 后拿到了**商人商品清单**（`traderWord` 数组，见 §2.5），于是可以逐区对账：

| 区域 | 钥匙 | 源码商人售出 | 基准帖 merchantKeys | 一致 |
|---|---|---|---|---|
| 一区 | 黄 | 5（第 7 层） | 5 | ✅ |
| 一区 | 蓝 | 1（第 6 层） | 1 | ✅ |
| 二区 | 蓝 | 1（第 15 层） | 1 | ✅ |
| 二区 | 黄 | 0 | 0 | ✅ |
| 五区 | 黄 / 蓝 | 0 | 0 | ✅ |
| 四区 | 黄 | 8（第 31 层 5 + 第 38 层 3） | 7 | ⚠️ 差 1 |
| 四区 | 蓝 | 3（第 39 层） | 4 | ⚠️ 差 1 |

**5 项完全吻合，四区两项各差 1。** 这足以证明「基准帖的 merchantKeys = 商人售出钥匙」这个判断方向正确，
并解释了绝大部分差异；四区剩余的 1 把出入未解释（可能是基准帖把某处地图钥匙记成了商人出售，
或第 28 层的「回收黄钥匙」被计入）。**不应声称「完全吻合」。**

校验器据此把该检查降级为警告而非失败 —— 因为差异有据可查，属于**统计口径不同**而非漏装。

**金币差异的成因：** 基准帖的 `18145` 是**分段累计序列的末值**，反映的是「按攻略最优路线实际能拿到的金币」；
而本项目的 `21842` 是**地图上所有怪物金币的算术总和**（全清）。两者口径不同：
全清收益必然高于最优路线收益，因为最优路线会主动跳过部分怪。

## 5. 复现与再生成

```bash
# 1. 重新导入地图（会覆盖 data/floors/、index.json、monster-placement.json）
node tools/import-mota50.mjs

# 2. 全量校验
node tools/validate-data.mjs

# 3. 重新生成可视化校验台（内联数据随之更新）
node tools/build-balance-check.mjs
```

**顺序要求：** 导入 → 校验 → 生成校验台。
`build-balance-check.mjs` 会把 `data/*.json` 的当前内容内联进 HTML，
而 `validate-data.mjs` 的 H 段会逐字段比对两者是否一致 —— 所以**改完数据必须重新生成 HTML**，
否则防漂移检查会报错。这是有意设计：让「忘了同步」变成可见的失败，而不是静默的数值分叉。
